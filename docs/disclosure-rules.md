# Правила раскрытия фактов

Каждый факт сценария несёт условие, при котором заявитель вправе его назвать.
Условие пишется в поле `disclosure` факта в `drizzle/seed/scenarios/*.json` и
проверяется движком детерминированно, без обращения к модели: одно и то же
состояние звонка всегда даёт один и тот же набор доступных фактов, иначе занятие
перестало бы быть воспроизводимым.

Документ адресован автору сценария. Как устроен движок целиком — в
[`docs/scenario-engine.md`](scenario-engine.md).

## Сводка

| Правило | Факт открыт, когда | Проверка в коде | Занято в сценариях |
| --- | --- | --- | --- |
| `immediate` | всегда | — | 4 факта |
| `on_question` | оператор спросил об этом | разбор вопроса моделью, иначе `keywords` | 26 фактов |
| `after_turns` | заявитель уже говорил N раз | `callerTurns >= turns` | не занято |
| `below_panic` | заявитель не выше указанной ступени | `panicLevel <= level` | 2 факта |
| `after_stage` | звонок дошёл до стадии | порядок стадий | не занято |
| `never` | никогда | — | 4 факта |

`after_fact` удалено — см. последний раздел.

## `immediate`

```json
{ "type": "immediate" }
```

Доступен с первого хода и до конца звонка. Это то, с чем человек звонит: он не
ждёт вопроса, чтобы сказать главное.

```json
{
  "key": "incident_type",
  "displayLabel": "Что горит",
  "promptValue": "Горит квартира на пятом этаже, дым идёт по всему подъезду.",
  "disclosure": { "type": "immediate" }
}
```

В каждом из четырёх сценариев таким сделан ровно один факт — тип происшествия. И
это разумная норма: два-три `immediate`-факта означают, что заявитель выложит
всё сам и спрашивать будет нечего.

Такой факт обычно уже содержится в `openingLine`. Движок это учитывает: после
первой фразы он отмечает раскрытыми все факты, слышные в её тексте, чтобы
заявитель не «сообщал» их во второй раз как новость.

## `on_question`

```json
{ "type": "on_question", "keywords": ["адрес", "улиц", "где ", "куда ехать"] }
```

Факт открывается, когда оператор о нём спросил. Рабочая лошадка: 26 фактов из
34. В этом правиле и состоит смысл тренажёра — диспетчер обязан **спросить**. Не
спросил про этаж, заявитель сам не скажет, и обязательный вопрос останется
открытым до конца звонка.

О чём спросил оператор, решает модель, а не список слов: перед сборкой контекста
уходит короткий служебный запрос с каталогом фактов (идентификатор, подпись,
вопрос чек-листа — без содержания), и ответ модели подменяет проверку по словам.
Поэтому «кто дома?» открывает факт, для которого автор написал «люди» и
«внутри».

Ключевые слова при этом обязательны и остаются нужны:

- когда модель не ответила за 2,5 с, отдала ошибку или сломанный JSON;
- в ручных прогонах и тестах, где разборщик не подключён;
- в сортировке доступных фактов: «прямой ответ на вопрос» до сих пор
  определяется по ним, и на верхних ступенях паники, где в ход проходит один
  факт, это решает, какой именно.

Как их писать: слова ищутся **подстрокой** в нормализованном тексте (регистр, ё
и пунктуация не считаются), поэтому «адрес» находится и в «адреса», и в
«адресу» — падежи перечислять не нужно, достаточно основы. Обратная сторона —
случайные попадания: «дом» находится внутри «домофона», поэтому основу стоит
брать такой, чтобы она не встречалась в чужих словах, либо писать её с пробелом
(«где », «вы где»).

## `after_turns`

```json
{ "type": "after_turns", "turns": 3 }
```

Факт открывается, когда заявитель говорил не меньше указанного числа раз.
Считаются ходы **заявителя**, включая первую реплику, а не вопросы оператора.

Для того, что человек в шоке вспоминает не сразу: первые полминуты он кричит про
огонь, а на четвёртом ходу вдруг добавляет, что в квартире газовый баллон. Ни
одним сценарием пока не используется.

## `below_panic`

```json
{ "type": "below_panic", "level": 2 }
```

Факт открывается, когда ступень паники **не выше** указанной — проверка
`panicLevel <= level`, то есть на самом значении факт уже доступен.

Это награда за деэскалацию: пока человек кричит, он физически не вспоминает
цифры. Поэтому за правилом держат точные сведения — код домофона в S-015, «свет
никто не трогал» в S-047.

```json
{
  "key": "door_code",
  "displayLabel": "Код двери",
  "promptValue": "Код домофона один-К-сорок пять.",
  "disclosure": { "type": "below_panic", "level": 2 }
}
```

**Ловушка.** Правило работает вместе с `panicFloor` версии: ступень не может
опуститься ниже пола, поэтому `level` меньше `panicFloor` делает факт
недостижимым навсегда, и схема такую ошибку не поймает. В S-015 пол равен 2 и
код двери открывается ровно на 2 — то есть стажёр обязан опустить заявителя на
самое дно шкалы, а поскольку на этот факт ещё и сослан обязательный вопрос, без
деэскалации чек-лист не закрыть. Так и задумано, но проверять такую связку нужно
осознанно.

## `after_stage`

```json
{ "type": "after_stage", "stage": "wrap_up" }
```

Факт открывается с указанной стадии и на всех последующих. Порядок стадий:
`offered` → `conversation` → `wrap_up` → `ended` / `declined`.

Для того, что всплывает на прощание: «а я перезвоню, если что?».

**Ограничение.** Перехода в `wrap_up` в коде сегодня нет ни в одном месте:
звонок идёт из `conversation` прямо в `ended`. Поэтому применимо только значение
`conversation`, а факт за `after_stage: wrap_up` не откроется никогда. Ни одним
сценарием правило не используется.

## `never`

```json
{ "type": "never" }
```

Факт не открывается ни при каких условиях. По одному такому в каждом сценарии, и
это всегда то, чего диспетчеру не выяснить: причина возгорания, номер машины,
когда пострадавший последний раз ел, звонили ли уже в газовую службу.

```json
{
  "key": "fire_cause",
  "displayLabel": "Причина",
  "promptValue": "Причина возгорания заявителю неизвестна.",
  "disclosure": { "type": "never" }
}
```

Зачем он нужен, если его нельзя получить: в разборе видно, что стажёр тратил
время на невыясняемое, а сам факт документирует границу знаний персонажа для
автора и преподавателя.

**Ограничение.** Содержание такого факта модель не получает никогда — в контекст
уходят только доступные факты. Поэтому фраза «причина мне неизвестна» берётся не
из `promptValue`, а из общей инструкции промпта: отвечать без новых сведений,
когда разрешённых фактов нет. Текст `never`-факта сегодня читает человек, а не
модель.

**Никогда не ссылайтесь на такой факт из `mandatoryQuestions`** — пункт
чек-листа станет невыполнимым, и схема этого не поймает. В текущих сценариях
таких ссылок нет.

## `after_fact` — удалено

Седьмое правило, которое существовало раньше:

```json
{ "type": "after_fact", "factKeys": ["trapped_children"] }
```

Факт открывался после того, как прозвучали все перечисленные факты. Так в S-015
и S-021 состояние пострадавших открывалось только после того, как заявитель уже
сказал, что внутри люди.

Убрано потому, что ломался естественный вопрос: на «Они дышат?», заданное
первым, заявитель молчал — сценарий держал факт закрытым, хотя человек на том
конце, конечно, ответил бы. Разбор вопроса моделью делает правило ненужным:
состояние пострадавших стало обычным `on_question`.

Цена решения: пункт чек-листа про состояние теперь может закрыться раньше пункта
про людей, и оценка больше не отличает последовательный опрос от случайного
попадания.

Сохранённые в базе версии сценариев переписала миграция
`0011_rewrite_after_fact.sql`: без неё загрузка старой версии падала на
неизвестном варианте правила. Если вам нужна последовательность вопросов как
требование, сейчас её выражает только чек-лист, а не правило раскрытия.

## Что правило не решает

Правило делает факт **доступным**, а не сказанным. Дальше идут ещё два фильтра,
и автор сценария должен их учитывать.

**Бюджет хода** по ступени паники: 3, 3, 2, 1, 1 новых факта. На верхних
ступенях в ход проходит один факт, даже если правила открыли пять. Уже
прозвучавшие факты доступны всегда — повторяться заявителю не запрещено.

**Выбор содержания**: из доступного берётся то, что относится к заданному
вопросу. Если спросили ровно о том, что правило держит закрытым, заявитель не
отвечает **ничем** — подставить вместо кода домофона номер дома хуже, чем
промолчать. Приоритет факта (`priority`) решает только спор между равными.

## `keywords` против `contentKeywords`

Два поля с похожими именами, которые легко спутать. Они описывают разные
стороны разговора:

| | `on_question.keywords` | `contentKeywords` |
| --- | --- | --- |
| Где живёт | внутри правила `disclosure` | рядом с фактом |
| Что описывает | вопрос оператора | ответ заявителя |
| С чем сравнивается | текст оператора | текст реплики заявителя |
| Способ поиска | подстрока | с начала слова |
| Зачем так | найти слово в любом падеже | «дет» обязано найтись в «детей» и не найтись в «видеть» |
| Что даёт | факт становится доступным | факт считается названным |

`contentKeywords` нужны потому, что модель обязана перечислять раскрытые факты в
`revealedFactIds` и регулярно этого не делает: заявитель отвечает «Там дети!», а
обязательный вопрос остаётся открытым. Факт без `contentKeywords` словами не
засчитывается никогда — молчаливое совпадение хуже пропуска.

## Чек-лист автора

- у факта есть `contentKeywords`, иначе он засчитается только по пометке модели;
- `below_panic` с `level` не ниже `panicFloor` версии;
- `after_stage` только со значением `conversation`, пока `wrap_up` недостижим;
- на `never`-факт не сослан обязательный вопрос и поле образцовой карточки;
- `immediate` — один-два факта на сценарий, иначе спрашивать будет нечего;
- основы в `keywords` не встречаются внутри чужих слов.

Проверить, как сценарий звучит на самом деле, быстрее всего так:

```bash
bun run audit:dialogue
```

Прогон показывает по каждому вопросу оператора, какой факт откроется и что
заявитель ответит.
