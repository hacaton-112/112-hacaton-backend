# Установка и эксплуатация

Подробный регламент с командами и мерами безопасности находится в [основной инструкции](../deployment.md). Ниже — краткий маршрут для ввода системы в учебную эксплуатацию.

## Требования

- Linux x86_64/arm64, например Ubuntu 22.04/24.04, Docker Engine и Compose v2.
- Без речевых моделей: ориентир 2 vCPU, 4 ГБ RAM, 20 ГБ диска. Размер базы, аудио и backup со временем растёт.
- Для CPU-контура ASR, Piper и двух GGUF-моделей нужны дополнительные RAM, CPU и место под модели; единой минимальной конфигурации проект не заявляет: её нужно подбирать под выбранные модели и одновременные сессии.
- Для первичной сборки нужен доступ к реестрам образов и зависимостей. После загрузки моделей и офлайн-карты основная работа возможна в локальной сети.

## Состав Docker Compose

| Группа | Сервисы |
| --- | --- |
| Приложение | `gateway`, `backend`, `postgres`, `postgres-backup` |
| Речь и модели | `asr`, `local-llm`, `tools-llm`, `piper-tts`; альтернативный CUDA TTS |
| Карта и хранилище | `tileserver`, `minio` |
| Наблюдаемость | `prometheus`, `grafana`; `pgadmin` для ручного администрирования |
| Телефония | `asterisk`, не требуется для работы ДДС |

## Настройка и запуск

1. Клонировать единый репозиторий: backend находится в `apps/backend/`, веб-клиент — в `apps/web/`.
2. Скопировать `.env.production.example` в `.env`, ограничить права на файл и заменить все `CHANGE-ME`.
3. Задать как минимум адреса/TLS, пароли PostgreSQL, MinIO, Grafana и pgAdmin, `JWT_SECRET`, CORS для раздельного dev-запуска, пути к двум GGUF-моделям и параметры ASR/TTS. Полный перечень и безопасные значения по умолчанию даны в шаблоне `.env.production.example`.
4. Проверить конфигурацию: `cd apps/backend && bun run ops:check`.
5. Запустить: `docker compose --profile app up -d --build`.
6. Проверить `docker compose ps`, журналы backend/gateway и `/api/v1/health`. Backend сам применит миграции Drizzle до начала приёма запросов.
7. Создать первого администратора и опубликовать демонстрационные сценарии командами из основной инструкции.

При остановке используйте `docker compose down` без `-v`: ключ `-v` удалит базу, аудио и метрики.

## Миграции и обновление

Миграции не откатываются вручную. До обновления делается backup, затем код и образы обновляются командой `git pull && docker compose --profile app up -d --build`. Если изменились исходные файлы сценариев, сид публикует новую версию только изменённого сценария.

## Резервное копирование

`postgres-backup` создаёт custom-format dump при старте и затем раз в сутки, проверяет его через `pg_restore --list` и пишет SHA-256. По умолчанию дампы в `var/backups` хранятся 14 дней.

```bash
docker compose --profile ops run --rm postgres-backup backup
docker compose --profile ops run --rm postgres-backup verify <файл.dump>
```

Восстановление заменяет рабочую базу. Нужно остановить gateway/backend, сделать страховочную копию и передать точное имя базы в `RESTORE_CONFIRM_DATABASE`. Restore проверяет checksum и идёт одной транзакцией. MinIO не входит в SQL-dump: его том архивируется отдельно при остановленном MinIO. Обе копии нужно выносить с сервера и ежемесячно проверять восстановление.

## Пакет сценариев

Перенос учебных данных между контурами выполняется через экспорт/импорт JSON-пакета сценариев. Пакет содержит номер формата, время экспорта и массив сценариев. Импорт сначала валидирует заголовок, каждую запись и уникальность кодов; режим `dryRun` возвращает отчёт без записи. Подписи и checksum пакета нет, поэтому полученный файл нужно передавать по доверенному каналу. Операция доступна преподавателю и администратору. Перед импортом в рабочий контур храните исходный пакет и дамп базы вместе.
