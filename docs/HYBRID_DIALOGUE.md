# Подготовленные реплики и локальная LLM

Первый этап — issue #106, инструкторский процесс второго этапа — #112 (app #72).
Модели не скачиваются автоматически этой фичей, настройки
действующего окружения не изменяются. Это не подтверждение работы десяти
одновременных звонков на шестиядерном CPU.

## Что реализовано

При явной публикации сценария в одной транзакции создаются неизменяемая версия
и задание `scenario_audio_packs`. Фоновая подготовка берёт утверждённые
преподавателем `openingLine`, `fallbackLine`, `facts[].promptValue`, несколько
безопасных реакций и варианты подтверждения. Для них создаётся PCM с голосом,
темпом и эмоцией каждой разрешённой ступени паники. Новые факты и геоданные
не генерируются. Длинные факты не обрезаются: если текст превышает лимит реплики,
он не попадает в набор подготовленного аудио.

Это банк отдельных ответов, **не сгенерированный линейный диалог**. Второй этап
добавляет подготовку снимка **до публикации**, редактор вопросов, явное утверждение,
прослушивание и атомарную привязку готового набора. Подробности ниже.

Набор связан с `scenarioVersionId`. Старые звонки не получают аудио новой версии;
изменение адреса, фактов, голоса или правил публикуется новой версией и требует
новой подготовки. Имя объекта включает версию, SHA-256 текста/параметров и SHA-256
аудио. Готовый набор не пересоздаётся автоматически при замене TTS-модели.

Во время звонка:

1. Точное совпадение с вопросом чек-листа или утверждённым вариантом (без учёта регистра, пунктуации и `ё`)
   разбирается без LLM. Это не поиск подстроки: отрицания не отбрасываются.
2. Перефразированный вопрос проходит через существующий заменяемый разборщик.
   Его кеш учитывает сессию и весь каталог вопросов/подписей, а не только ключи фактов.
3. Scenario Engine применяет условия раскрытия, состояние и план реакции.
4. Для распознанного вопроса, не более одного выбранного факта и реакции
   `answer`, `repeat` или `acknowledge` проверяется точное аудио безопасной реплики
   движка. Совпадение готового набора пропускает генерацию текста и TTS.
5. Для сложных реакций, нескольких фактов, неподготовленных сценариев или промаха
   продолжается прежний модельный конвейер. Первая реплика также переиспользует аудио.
   Если результат модели или fallback дословно совпал с подготовленной репликой,
   аудио тоже переиспользуется; источник и попытки генерации при этом сохраняются.

Аудио не выдаётся оператору пакетом. Только текущая разрешённая реплика проходит
обычный WebSocket, запись разговора и механизм перебивания. В событиях/метриках
есть `source: prepared`, `attempts: []`: отсутствующие вызовы моделей не считаются
успешными вызовами. Старый desktop-клиент нужно обновить, чтобы он принимал новый
вариант `source`.

## Устойчивость подготовки

- Очередь и прогресс находятся в PostgreSQL, PCM — в существующем приватном S3/MinIO.
- Один действующий worker lease на кластер backend; срок 120 секунд, TTS ограничен
  90 секундами. После падения процесса просроченный lease подбирается снова.
- Сохраняется каждый завершённый объект. Повтор после ошибки продолжает задание.
- Во время активного разговора новые объекты не синтезируются. Проверка раз в секунду
  отменяет уже идущий синтез, если начался разговор. Runtime TTS тоже должен уважать
  отмену HTTP-запроса; фактическое освобождение вычислительных ресурсов зависит от него.
- Незавершённый набор не используется. Ошибка или несовпадение хеша — промах кеша,
  не завершение звонка. Чтение аудио ограничено 750 мс, один объект — 8 MiB.
- Готовые объекты сохраняются без публичных URL. Авторизация REST: instructor/admin.

## Включение

1. Применить миграцию `0019_scenario_audio.sql` штатным `bun run db:migrate` после
   проверки миграционного журнала на тестовой БД. Миграция создаёт только новую
   таблицу. В исходном репозитории уже есть SQL/snapshot 0016–0018, отсутствующие
   в журнале; эта задача их не переисполняет и не исправляет их историю. Существующую
   схему session recovery требуется проверить отдельно перед чистым развёртыванием.
   Для второго этапа также нужна `0020_dialogue_preparations.sql`: новая таблица
   снимков и `scenario_audio_packs.entries`. На момент реализации `db:generate`
   останавливается из-за существующей коллизии родителей snapshots 0016/0019.
   Поэтому 0020 — отдельная custom SQL-миграция, зарегистрированная в журнале,
   без нового автоматически сгенерированного snapshot. Она не исправляет baseline.
   Не используйте `db:push` как обход этого конфликта. Миграцию сначала проверьте
   на копии своей БД; рабочая БД при разработке этой фичи не изменялась.
2. Настроить существующие `CALL_RECORDING_S3_*`: доступ к приватной корзине нужен
   подготовке даже если запись звонков выключена.
3. Убедиться, что локальный TTS работает, и задать `SCENARIO_AUDIO_WORKER_ENABLED=true`.
4. В конструкторе заполнить обязательные поля, включая место происшествия.
   В блоке «Подготовка диалога и голоса» сохранить текущий снимок. Проверить вопросы,
   сохранить правки, нажать «Тексты проверены — утвердить и озвучить».
   Дождаться готовности, прослушать ответы и отдельно опубликовать сценарий.
   Старый способ подготовки уже опубликованной версии остаётся совместимым.

REST под `/api/v1`: `GET` и `POST`
`/scenarios/versions/:scenarioVersionId/audio-preparation`. POST идемпотентен для
готового/выполняющегося задания; после ошибки возобновляет его. Ответ содержит
только `scenarioVersionId`, `status`, `completed`, `total`, `workerEnabled`.

## Второй этап: проверяемый инструктором банк

Состояния: `queued → generating → review → synthesizing → ready → published`.
Без AI снимок сразу попадает в `review`. Ошибка AI после двух попыток переводит
его в ручную проверку с исходными вопросами и предупреждением. Ошибка TTS
даёт `failed`; явное продолжение сохраняет уже завершённые записи.

- AI включается преподавателем отдельно, по умолчанию выключен. Настроенному
  `LLM_PROVIDER` передаются **только исходные вопросы оператора**, по одному факту
  за задание. Поля адреса, координаты, ответы и transcript не отправляются.
  Вопросы должны быть синтетическими: текст вопроса сам может содержать данные,
  если их ввёл преподаватель. В UI есть предупреждение о локальном/облачном провайдере.
- Модель предлагает до трёх перефразировок; редактор допускает до четырёх вопросов
  на факт. Для факта без исходного вопроса AI не придумывает тему — его вопросы
  преподаватель добавляет вручную. Семантическое соответствие проверяет человек.
- Ответ — точный `promptValue` либо `Хорошо. ` + `promptValue`. Произвольный новый
  фактический текст не принимается в контракте банка. Содержание меняют в разделе
  фактов и создают новый снимок. Для полного покрытия факт ограничен 492 символами
  (общий лимит речи — 500); слишком длинная реплика блокирует подготовку, не обрезается.
- Снимок хеширует весь нормализованный сценарий и ревизию компилятора. Включены
  адрес, обе точки, радиус, голос, факты и условия раскрытия. Повтор создания с тем же
  владельцем и хешем возвращает то же задание. Смена checkpoint TTS автоматически
  не обнаруживается: готовое аудио остаётся прежним; смена профиля компилятора требует
  новой ревизии его ключа. Это не автоматическая миграция моделей.
- Сохраняются исходные `authoringSource/authoringPrompt`. Восстановление доступно
  из последних 20 неопубликованных подготовок своего аккаунта. Несохранённые правки
  вопросов не переживают закрытие формы; сначала нажмите «Сохранить правки».
- Правки банка защищены `revision`; публикация проверяет владельца, утверждение,
  полноту аудио и хеш текущей формы под блокировкой строки в одной транзакции с новой
  версией. Готовые entries/assets копируются в приватный `scenario_audio_packs` версии.
  Опубликованный банк нельзя вернуть в редактирование. Старые сессии неизменны.
- Две очереди используют общий advisory lock и lease: одновременно тяжёлую работу
  выполняет одно задание. Черновики имеют приоритет перед legacy-подготовкой.
  Проверка активных звонков останавливает новую работу и отменяет текущую; отменённый
  результат не считается готовым. Прогресс сохраняется после каждого факта/PCM-объекта.
- Возврат к проверке увеличивает ревизию, отменяет результат старого worker и снимает
  утверждение. Уже записанное аудио сохраняется: вопросы и безопасный префикс не меняют
  факты/голос снимка. Объекты не удаляются автоматически (включая orphan после сбоя).
- Полный банк и WAV-preview доступны только создателю с ролью instructor/admin.
  Оператор получает лишь текущую разрешённую реплику. Все ручные переходы аудитируются.

REST под `/api/v1/scenarios/dialogue-preparations`:

| Метод и путь | Назначение |
| --- | --- |
| `POST /` | `{scenario, useAi, authoringSource, authoringPrompt?}` — идемпотентный снимок |
| `GET /` | Последние 20 своих неопубликованных подготовок |
| `GET /:id` | Состояние, редакция, варианты, прогресс и перечень preview |
| `GET /:id/snapshot` | Восстановление формы и её происхождения |
| `POST /:id/review` | `{revision, entries}` — сохранить правки вопросов/префикса |
| `POST /:id/approve` | `{revision}` — утвердить и поставить озвучку в очередь |
| `POST /:id/reopen` | `{revision}` — снять утверждение и вернуться к проверке |
| `POST /:id/retry` | `{revision}` — продолжить после сбоя TTS |
| `GET /:id/audio/:index` | Приватный WAV, проверенный SHA-256, без публичного URL |

Оба endpoint публикации принимают необязательный `preparationId`. Без него
сохраняется старый workflow. В UI выбранный неготовый/устаревший снимок блокирует
публикацию; явное «Продолжить без этого набора» возвращает обычную публикацию.

Не реализована свободная генерация ответов, семантический поиск по embeddings,
автоматическое удаление старых пакетов или доказанная ёмкость CPU для 10 звонков.
Парафразы сопоставляются точно после нормализации; для остальных вопросов остаётся
существующий ограниченный LLM-путь. ASR второго этапа не менялся.

## Локальная LLM

```dotenv
LLM_PROVIDER=local
LOCAL_LLM_BASE_URL=http://127.0.0.1:8080/v1
LOCAL_LLM_MODEL=training-model
LOCAL_LLM_TIMEOUT_MS=30000
LOCAL_LLM_CONCURRENCY=1
# LOCAL_LLM_API_KEY=...  # только если локальный сервер требует авторизацию
```

`training-model` — alias реально загруженной модели в `llama-server`, а не имя
скачиваемого checkpoint. Compose собирает сервер из закреплённого commit
официального `microsoft/BitNet`, скачивает `BitNet-b1.58-2B-4T` в нативном
формате `I2_S` и запускает только на CPU. Используются JSON Schema, SSE для реплик,
`chat_template_kwargs.enable_thinking=false` и `reasoning_effort=none`.
Настройку non-thinking необходимо проверить с chat template выбранной модели.

Опубликованный GGUF не содержит `tokenizer.ggml.pre` и включает chat template,
который отличается от исходного Transformers checkpoint. Поэтому compose явно
задаёт pre-tokenizer `gpt-2` и поставляет шаблон из `tokenizer_config.json`.
Без этих двух исправлений модель повторяет промпт или генерирует бессвязный текст.

Профиль по умолчанию настроен на Ryzen 5 5600 по локальному замеру: 8 потоков
для decode (лучший результат среди 4/6/8/12), 12 SMT-потоков для prefill, два
независимых prompt-cache слота, по 4096 токенов на слот, `mmap + mlock`, Flash
Attention и KV cache `q8_0`. Для другого CPU начните с числа физических ядер
для `LOCAL_LLM_THREADS`, числа логических потоков для
`LOCAL_LLM_THREADS_BATCH`, затем прогоните свой benchmark. Проверка запуска:

```bash
docker compose build local-llm
docker compose up -d local-llm
docker compose exec local-llm curl -sf http://127.0.0.1:8080/health
```

Модель официально помечена как преимущественно англоязычная и исследовательская.
Для русскоязычного тренажёра обязательны приёмочные диалоги: выигрыш CPU не
считается достаточным, если модель хуже соблюдает роль, JSON-схему или факты.
Локальный smoke-test подтвердил transport и строгое JSON Schema, но ответ на
русский аварийный запрос оказался семантически непригодным. Поэтому этот профиль
готов для нагрузочного эксперимента, но не должен считаться принятым production
провайдером до прохождения русскоязычного набора качества.

Один лимит конкурентности разделяют реплики, разбор вопросов и инструменты
конструктора/грамматики. Лишний запрос не ждёт в неограниченной очереди; модельная
реплика переходит к безопасному fallback. Разбор вопроса имеет отдельный предел
2,5 секунды. При ошибке локальной модели **нет перехода на Alice AI**.
Ключи Alice не требуются. `LLM_PROVIDER=alice` сохраняет предыдущий режим.

После review-fix фоновые `complete` резервируют последний слот для разговора.
Поэтому при `LOCAL_LLM_CONCURRENCY=1` AI-подготовка вопросов намеренно недоступна:
можно проверять вопросы вручную. Для AI-предложений в фоне нужен лимит минимум 2
и runtime, который действительно выдерживает такую конкурентность. Worker не
обходит этот резерв и при недоступности AI возвращается к ручной проверке.

LLM-ответы проходят существующую проверку JSON и фактов. Эта проверка не является
доказательством отсутствия семантических галлюцинаций в свободном тексте; для
локальной модели нужен отдельный набор приёмочных диалогов. Подготовленный путь
этой неопределённости не имеет: произносит утверждённый текст движка.

## Что ещё нужно для полностью CPU-only контура

- Выбрать и измерить Whisper-модель/квантизацию на целевом сервере; CPU final-only
  профиль в `asr-service` не доказывает достаточной пропускной способности.
- Выбрать CPU TTS для **нового** текста или расширить покрытие подготовленных ответов.
  Текущий Qwen TTS runtime не становится CPU-оптимизированным от включения кеша.
- Измерить долю prepared/model/fallback, ASR latency, LLM TTFT/total, TTS TTFA,
  end-to-end p50/p95 на 1/3/5/10 одновременных звонках.
- Провести живой сквозной прогон с PostgreSQL, MinIO, TTS, ASR и bitnet.cpp:
  публикация → подготовка → звонок → перебивание → запись → разбор.
- Расширять утверждённые парафразы и безопасные реакции по измеренным промахам.

Runtime: [microsoft/BitNet](https://github.com/microsoft/BitNet). Протокол сервера:
[llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
