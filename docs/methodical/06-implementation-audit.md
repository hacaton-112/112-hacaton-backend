# Аудит реализации методических материалов

Дата актуализации: 17 сентября 2026 года. Ветка backend и desktop app:
`feature/metodik`.

## 1. Реализованный объём

Методические материалы перенесены из комплекта документов в рабочий продукт:

- backend отдаёт доступный пользователю каталог через
  `GET /api/v1/methodical-materials`;
- отметка раздела сохраняется через
  `PUT /api/v1/methodical-materials/:materialId/sections/:sectionId/completion`;
- прогресс хранится по паре «пользователь — материал — раздел» в таблице
  `methodical_section_progress`;
- desktop app содержит отдельный пункт меню и адаптивный экран с перечнем
  материалов, раскрываемыми разделами и индикаторами прогресса;
- оператор видит практикумы оператора 112 и ДДС;
- преподаватель и администратор дополнительно видят руководство преподавателя,
  методику оценивания и форму протокола занятия.

Каталог содержит 4 материала и 13 разделов. Текст API основан на ТЗ 2026,
памятке АРМ-112 ДДС, учебных билетах и классификаторе v046, использованных при
подготовке основного комплекта.

## 2. Сверка с фактической реализацией

| Область                | Результат сверки                                                               |
| ---------------------- | ------------------------------------------------------------------------------ |
| Роли                   | Совпадают с моделью продукта: `operator`, `instructor`, `admin`                |
| Авторизация            | Оба маршрута защищены `JwtAuthGuard`                                           |
| ДДС: первичное решение | `Принята` / `Не принята`, норматив 30 секунд                                   |
| ДДС: цепочка           | Принята → Начало реагирования → Прибытие → Проведение работ → Работы завершены |
| ДДС: комментарии       | Обязательны для `Не принята` и `Отказ от выполнения работ`                     |
| ДДС: оценка            | 40 баллов за норматив и 60 за завершение; отказ даёт 20 вместо 60; порог 75    |
| Учебный звонок         | Веса 35 / 35 / 15 / 15 совпадают с `debrief/domain/evaluation.ts`              |
| Версионность сценария  | Оценка и карточка связаны с опубликованной версией сценария                    |
| Клиентский контракт    | Ответ API проверяется Zod-схемами до отображения                               |
| Миграция               | `0018_long_secret_warriors.sql`, применена на локальной БД                     |

В ходе аудита исправлено расхождение раннего текста экрана с конечным автоматом
ДДС: вымышленные подписи `Назначено`, `В пути`, `На месте`, `Завершено` заменены
точными статусами продукта, добавлены `Не принята`, `Проведение работ` и
`Отказ от выполнения работ`. На время записи прогресса остальные кнопки
блокируются, чтобы параллельные ответы не перезаписывали клиентский кэш в
неверном порядке.

## 3. Проверки

- backend: ESLint, TypeScript typecheck и production build проходят;
- тесты нового backend-контента: 2 из 2 проходят;
- desktop app: production build проходит;
- desktop app: 68 из 68 тестов проходят, включая контракт материалов;
- живой smoke-тест под администратором подтвердил получение 4 материалов и 13
  разделов, установку отметки и её обратное снятие;
- `git diff --check` не выявил ошибок пробелов.

Общий набор backend дал 827 успешных тестов. Шесть существующих тестов вне
этого модуля нестабильны в текущем Windows-окружении: два связаны с занятым
портом метрик, один — с таймером voice pipeline, три — с различием Windows-пути
к тестовому WAV. Эти сбои не воспроизводятся в целевых проверках методических
материалов.

## 4. Остаточные ограничения

1. Содержание сейчас версионируется вместе с backend и не редактируется из
   административного интерфейса.
2. Прогресс доступен самому пользователю; сводный отчёт преподавателя по
   изучению материалов пока отсутствует.
3. В продукт не встроены PDF/XLSX-экспорт протокола занятия и печатная форма;
   Markdown-шаблон фиксирует согласованный состав данных.
4. Изменение прогресса пока не включено в общий audit trail. Если отметка будет
   использоваться как формальное подтверждение обучения, её необходимо писать
   в журнал аудита и запретить обучающемуся снимать подтверждение без причины.
5. Автотест UI проверяет контракт, но не выполняет скриншотную регрессию экрана.

## 5. Рекомендованные следующие шаги

1. Добавить преподавателю сводку прогресса по группе и выгрузку протокола.
2. Решить, является ли отметка «изучено» информационной или юридически значимой;
   во втором случае включить неизменяемый audit trail.
3. Добавить компонентный тест экрана на ролевую выдачу, ошибку API и повторный
   запрос.
4. Устранить шесть Windows-зависимых падений общего backend-набора отдельно от
   этой функциональности.

## 6. Дополнение: bootstrap классификатора

После аудита при запуске чистой БД обнаружена ошибка
`CLASSIFIER_ACTIVE_VERSION_NOT_FOUND`: общий сид создавал администратора и
сценарии, но не импортировал классификатор. В репозиторий добавлен исходный XLSX
официальной версии v046 и идемпотентный шаг `db:seed:classifier`.

Теперь `bun run db:seed` последовательно создаёт администратора, импортирует и
активирует классификатор, затем загружает сценарии. Повторный запуск сверяет
SHA-256 файла и не создаёт новую версию. На локальной БД импортирована версия 1:
1283 записи, 139 диагностических предупреждений. Живой запрос
`GET /api/v1/classifiers/active/tree` вернул HTTP 200, 24 корневые группы и
1283 доступные администратору конечные записи.

## 7. Дополнение: редактор Markdown

Актуализация от 22 сентября 2026 года устраняет первое ограничение аудита:

- преподаватель и администратор создают материал через
  `POST /api/v1/methodical-materials` и редактируют через
  `PUT /api/v1/methodical-materials/:materialId`;
- общие сведения, роли доступа и упорядоченные разделы хранятся в таблице
  `methodical_materials`, добавленной миграцией `0026_methodical_materials.sql`;
- встроенные материалы продолжают работать без переноса данных, а первая правка
  создаёт в БД запись с тем же стабильным идентификатором;
- содержимое каждого раздела хранится в Markdown, проходит Zod-валидацию и
  отображается клиентом без выполнения встроенного HTML;
- удаление раздела удаляет только устаревший прогресс по этому разделу;
  прогресс остальных стабильных разделов сохраняется;
- создание и редактирование записываются в общий audit trail.

Удаление материалов, история редакций и назначение отдельных материалов группе
в этот этап не входят. Для юридически значимых материалов следующим отдельным
шагом нужна неизменяемая версия публикации, а не перезапись текущего черновика.
