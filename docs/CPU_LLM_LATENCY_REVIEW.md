# CPU: оптимизация задержки текстовой LLM

## Актуализация: issue #122, 20 сентября 2026

Предыдущие изменения ниже уже слиты через PR #120 (`651f3f5`). Исторические
сведения о среде и локальных ветках относятся к предыдущему прогону.

Ветка `122-avoid-redundant-generation`:

- Исправлено: отсутствие готовой записи больше не отправляет разрешённый
  Scenario Engine текст на повторную генерацию. Обычный и offline-конвейеры
  сразу синтезируют этот текст; повторного поиска того же аудио тоже нет.
- Исправлено: локальная LLM не перегенерирует корректный ответ ради стилистики.
  В literal-режиме текст не обрезается удалением ранее сказанных предложений.
  Политика задаётся адаптером; поведение облачного адаптера не менялось.
- Сохранено: проверка разрешённых фактов, общего offline-deadline, отмены,
  целостности TTS; одна повторная попытка при невалидном JSON и безопасный fallback.
- Метрики: `generation.source=prepared`, `attempts=[]` означают выбор текста
  без LLM. При живом синтезе offline `resolution.path=local-generated` остаётся
  прежним: это не доказательство вызова текстовой модели. Проверять также
  `synthesis.source` и число generation attempts.
- Модель, `.env`, ASR и app не менялись. Fine-tuning Qwen3-0.6B ведёт напарник.

Следующий этап — отдельные issues/ветки ДДС: самостоятельный режим карточек
для обучающегося, назначение и оценка преподавателем; голосовая передача —
следующий этап. Это не реализовано данным исправлением голосового конвейера.

Проверки этого изменения на macOS через Bun: typecheck, lint, build — успешно;
полный Jest-прогон — 122 набора, 1117 тестов успешно. Живые замеры на целевом
CPU и тест десяти звонков не выполнялись; ускорение в миллисекундах не заявляется.

## Что исправлено

- Готовая запись выбирается после решения Scenario Engine независимо от
  `preferPreparedReply`. Проверяются разрешённые факты, тип реакции и число
  выбранных фактов. Панический отказ не заменяется фактическим ответом.
- Готовые нефактические реакции движка, включая успокоение и уточнение,
  также могут обходить генерацию. Ошибка intent, deadline и prompt injection
  по-прежнему ведут в безопасную offline-обработку.
- Восстановлены общий offline-срок, отмена зависшего intent-провайдера и
  сохранение решения для `recordReply`. Успешный разбор при записи не повторяется.
- Убран обход распознавания только в production/local, возвращавший
  `undefined as string[]`: тесты и production теперь используют один маршрут.
  Неизвестную формулировку снова разбирает классификатор; это сознательное
  восстановление безопасности, а не обещание нуля LLM-вызовов на любой фразе.
- Локальный классификатор получает только каталог вопросов/подписей, возвращает
  `askedFactIds` из ограниченного `enum`, работает с `temperature=0`.
  Добавлены указания об отрицаниях, нескольких вопросах и разных участниках.
  Его качество на реальных моделях ещё нужно измерить.
- Локальная генерация возвращает только `{text, revealedFactIds}`. Эмоция,
  интенсивность, темп и завершение звонка подставляются из fallback движка.
  Без fallback используются прежние безопасные значения по умолчанию.
  Подстановка выполняется при первом реальном токене, а не до ответа модели;
  TTFT не «ускоряется» искусственным событием. Неожиданные поля отклоняются.
- Восстановлена инструкция `literalFactReplies`; offline-проверка текста остаётся.
  Лимит ответа настраивается через `LOCAL_LLM_REPLY_MAX_TOKENS`, по умолчанию 128.
  Это верхний предел, не требование генерировать 128 токенов; прежних 80 с полным
  JSON могло не хватать. Частоту обрывов нужно проверить на модели.
- Удалены фиксированные `id_slot=0/1`: свободный слот выбирает llama-server.
  `cache_prompt` сохранён, но попадание в кеш не гарантируется при смене истории.
  Backend concurrency по умолчанию остаётся 1, очередь ограничена.
- HTTP 400/408/429 не вызывают немедленную повторную попытку генерации.
- Убраны неиспользуемые импорты глобального env; фабричные тесты больше не
  блокируются ESM-импортом `@t3-oss/env-core`.

Ожидаемые маршруты при наличии записи и разрешении движка:

| Маршрут | Intent LLM | Генерация ответа | Живой TTS |
|---|---:|---:|---:|
| Точный утверждённый вопрос | 0 | 0 | 0 |
| Перефразированный вопрос, распознан один факт | 1 при промахе кеша | 0 | 0 |
| Повтор уже разобранной формулировки в той же сессии | 0 | 0 | 0 |
| Нужной записи нет, есть разрешённые факты | возможен | ограниченная | возможен |

Несколько фактов, неоднозначность и отрицания не сводятся к ближайшему
совпадению строки. Готовый аудиовыход сам по себе не доказывает отсутствие
предыдущего intent-вызова.

## Измеренные здесь результаты и границы

Доступная среда: Linux aarch64, два виртуальных ядра Apple; это не целевой i7.
Docker и Bun отсутствуют. Проверки выполнялись через Node 24 и локальные зависимости.

- До исправлений выбранные тесты: 17 прошли, два набора фабрики не запускались
  из-за ESM-импорта.
- После первой ветки: 51 тест маршрутизации/offline прошёл, typecheck и lint прошли.
- Финальный полный прогон: **122 набора, 1110 тестов прошли**. Первые два отказа
  TCP-тестов метрик были вызваны `listen EPERM` в песочнице; полный повторный
  прогон с разрешённым localhost прошёл целиком. Typecheck и lint — без ошибок.
- Тест десяти конкурентных prepared-ходов проверяет отсутствие вызовов генерации
  и синтеза и завершение потоков. Хранилище подменено: **это не нагрузочный тест**.
- Системный промпт ответа: 1744 → 470 символов; strict offline — 631 символ.
  Пример `Во дворе.`: полный JSON 115 → компактный JSON 48 символов.
  Это символы, не токены и не замер задержки.

Исходные логи/таблицы сравнения 1Bit/BitNet и Qwen в репозиториях не найдены.
Выбрать победителя по пользовательскому значению 30 токенов/с нельзя.
При этой скорости 60 токенов — около 2 с, 80 — около 2,7 с **только decode**:
не включены обработка промпта, ожидание, ASR, проверка и TTS. Разные токенизаторы
также не позволяют сравнивать модели только по токенам/с.

## Настройки CPU: стартовая гипотеза, не оптимум

Compose: ASR 2 потока, LLM 4 decode / 4 batch, `poll=0`, два серверных слота,
backend concurrency 1. Все параметры потоков/слотов переопределяемы.
Это снижает агрессивное соперничество с Piper по сравнению с 6/12 потоками
и `poll=100`, но не резервирует ядра и может замедлить одиночный запрос.
Нужен A/B-замер полного стека. Piper/ONNX тоже потребляет CPU; его бюджет
этими настройками не ограничен. Не увеличивать concurrency без нагрузки.

Compose по-прежнему загружает Qwen2.5-3B-Instruct Q4_K_M по умолчанию,
несмотря на название коммита про 0.5B. Фактические файл и SHA модели надо
снять на сервере: переменные окружения могут переопределять значения.

Параметры слотов сверены через Context7 с
[исходниками llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-context.cpp).
Потоки и polling описаны в
[документации сервера](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
Тег образа `server` плавающий: в измерениях обязательно фиксировать digest.

## Piper и ASR: оставшиеся риски

Текущий Piper-адаптер выбирает голос по полу и учитывает темп через
`length_scale`. Эмоция и интенсивность не передаются провайдеру. Он загружает
полный WAV, пересэмплирует в 24 kHz PCM и выдаёт один финальный чанк.
Следовательно, асинхронный интерфейс адаптера не означает потоковый синтез.
При попадании в банк ни этот синтез, ни LLM не нужны; перенос в WebView
не является приоритетом данного изменения.

**Не исправлено в этих ветках:** `audioFingerprint` не включает провайдер,
версию TTS и версию голосовой модели. Старое аудио Qwen может переиспользоваться
после переключения на Piper. Нужен единый версионированный профиль синтеза во
всех workers, preview, публикации и lookup, затем явная переподготовка пакетов.
Просто повторный POST подготовки готового пакета его не обновляет (идемпотентен).
До такой миграции не считать смену провайдера для старых пакетов завершённой.

В ASR `bc6cb84` добавлены CPU flash attention и динамический `audio_ctx`.
Утверждение комментария «тот же текст в разы быстрее» замерами здесь не подтверждено:
нужен корпус с адресами, числами, короткими и длинными фразами для сравнения
ошибок распознавания и p95. Rust/Docker-прогон в этой среде не выполнялся.

## Воспроизводимые проверки и следующий замер

```sh
node node_modules/typescript/bin/tsc --noEmit
node node_modules/eslint/bin/eslint.js src test/manual/pipeline-stage-profiler.ts test/manual/local-intent-benchmark.ts
node node_modules/jest/bin/jest.js --runInBand --silent
node --import tsx test/manual/local-intent-benchmark.ts --dry-run
```

Новый `test/manual/local-intent-benchmark.ts` сравнивает локальные модели
на одном синтетическом корпусе из 12 вопросов: перефразирования, отрицание,
два вопроса, неизвестный факт, заявитель/пострадавший. Выводит JSONL с ожидаемыми
и фактическими ID, ошибками и p50/p95. Это небольшой smoke-корпус, не достаточный
набор для утверждения качества модели.

```sh
node --import tsx test/manual/local-intent-benchmark.ts --base-url=http://127.0.0.1:8080/v1 --model=training-model --rounds=3
```

Повторить с Qwen 0.5B/1.5B/3B и выбранной 1Bit-моделью при совместимом сервере.
Фиксировать модель/квантизацию/SHA, server digest, CPU, потоки и timeout.
Начальная задержка ограничена 2500 мс; `--timeout-ms=...` позволяет отдельно
исследовать более медленные модели. Первая холодная попытка не исключается.
Эти вызовы на модели **здесь не выполнялись**; проверен dry-run корпуса.

`pipeline-stage-profiler.ts` теперь вызывает фабрику и настоящий
`VoicePipelineService`, включая банк, offline-ветку и `recordReply`.
Фиксирует реальное время фабрики, вызовы/время intent-порта, попытки генерации,
resolution, TTS, запись хода и время до первого аудио. Нет распределения 85/15,
нет «токенов» по длине строки. TTFT включает ожидание и транспорт, это не
чистый prompt-eval. `source=prepared` нужно читать вместе с `resolution`:
безопасный fallback тоже может иметь такой source.

Профайлер создаёт записи звонка; запускать только на изолированной тестовой БД:

```sh
bun run profile:pipeline --allow-write --scenario=S-015 --turns=6
```

Он начинается с текста и не измеряет ASR, сеть до АРМ и фактическое воспроизведение.
Для проверки десяти звонков использовать существующий `load:calls` с настоящим
WAV речи, отдельными сценариями обычных и одновременных нестандартных вопросов.
Собирать долю bank-hit, intent/reply LLM-вызовы, ошибки/обрывы/повторы, очередь,
TTFT, prompt/decode timings сервера, p50/p95 до первого звука и загрузку всего CPU.
Готовность минимального i7 к десяти операторам пока не подтверждена.
