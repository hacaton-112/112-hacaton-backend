# CPU LLM benchmark

Дата замера: 2026-09-20. Хост: AMD Ryzen 5 5600, 6 ядер / 12 потоков, Docker Linux x86_64. Основной профиль: один последовательный запрос, `ctx-size=2048`, `batch-size=512`, `temperature=0`, 128 новых токенов. Новые замеры выполнены на 6 физических потоках после прогрева модели; для них приведена медиана прогонов. Старые результаты сохранены как среднее трёх прогонов.

TL2 теперь собирается и работает корректно на x86 AVX2. Greedy-вывод TL2 совпал с официальным I2_S. В decode TL2 быстрее I2_S на 9.7%, но prefill медленнее примерно в 1.95 раза. Поэтому TL2 выгоден для короткого prompt и длинного ответа, а I2_S — для больших входных контекстов.

Подбор потоков TL2 на Ryzen 5 5600: 6 / 8 / 10 / 12 потоков дали примерно 29.75 / 29.05 / 25.72 / 20.96 tok/s в предварительной серии. Лучший профиль — 6 физических потоков, SMT-потоки здесь мешают.

## Intel Core i7-8700

Контрольный замер выполнен 2026-09-20 на Intel Core i7-8700, 6 ядер / 12 потоков, AVX2, 12 MiB L3, Ubuntu 26.04 и Docker. Использованы тот же commit BitNet runtime `0b341e582afbf9e1011f24744b554c96a3477eb5`, исправления TL2 из ветки `feat/bitnet-cpu` и единый профиль: 512 входных токенов, 128 новых токенов, `ctx-size=2048`, `batch-size=512`, `temperature=0`, один последовательный запрос. Результат — медиана после прогрева.

На i7-8700 лучший TL2-профиль быстрее лучшего I2_S по decode только на 3.9%, но примерно вдвое медленнее по prefill. Qwen3 0.6B Q4_K_M быстрее TL2 в 2.35 раза по decode и в 5.29 раза по prefill. В отличие от Ryzen, 12 SMT-потоков немного быстрее 6 физических: +1.3% для TL2, +3.3% для I2_S и +6.4% для Qwen3.

По сравнению с Ryzen 5 5600 этот i7-8700 медленнее по decode: TL2 — примерно на 17.5%, I2_S — на 13.0%, Qwen3 0.6B — на 27.2%. Следовательно, специализированный BitNet kernel не делает i7-8700 быстрее Ryzen и не меняет выбор модели: для быстрого backend-профиля Qwen3 0.6B остаётся существенно выгоднее.

Во время теста контейнер занимал около 297 MiB RSS для TL2 и 515 MiB для Qwen3; mmap/page cache учитывается ОС отдельно. На хосте оставалось около 29 GiB доступной RAM, swap не использовался.

## Качество короткого smoke-теста

Проверялись три русских задания: простое объяснение цвета неба, арифметика `17 - 5 + 3`, строгий JSON `{"status":"ok","count":3}`.

| Модель | Результат |
| --- | --- |
| Qwen3 0.6B Q4_K_M | Единственная из новых малых моделей правильно решила арифметику и сохранила нужные JSON-поля. Добавила Markdown вопреки инструкции и ошиблась в физическом объяснении. Лучший быстрый кандидат, но только с серверной валидацией результата. |
| Qwen3-0.6B-rus-16384 Q4_K_M | Быстро и свободно пишет по-русски, но дала неверное объяснение, ответила `20` вместо `15` и сломала JSON-поля. Сокращённый словарь ускоряет decode, но текущая модель недостаточно надёжна для backend. |
| Gemma 3 270M-it Q4_K_M | Самая быстрая и компактная, но провалила объяснение и арифметику; русский текст деградирует и зацикливается. Подходит только для узкой задачи после отдельного fine-tune и eval. |
| BitNet b1.58 0.7B | Base-модель без instruction/chat tuning. Для backend непригодна без дообучения. |
| BitNet-b1.58-2B-4T | TL2 математически исправен, но сама модель зацикливается в проверенных русских запросах. Скорость ниже Qwen/Gemma. |
| Qwen2.5 0.5B Instruct | Быстрый API/JSON-профиль, но старый safety smoke-test выполнила неполно. Нужны жёсткая схема и fallback. |
| Qwen2.5 1.5B Instruct | Медленнее, но остаётся наиболее разумным кандидатом на качество среди протестированных размеров. Перед production нужен проектный eval. |

## Рекомендация для backend

- Быстрый профиль: **Qwen3 0.6B Q4_K_M**, около 82 tok/s. Обязательно валидировать JSON, ограничивать схему ответа и иметь deterministic fallback.
- Профиль качества: пока оставить **Qwen2.5 1.5B Instruct**, около 37 tok/s, и сравнить обе модели на реальных диалогах проекта.
- Gemma 270M и Qwen3-rus-16384 не включать по умолчанию: высокая скорость не компенсирует провал базовых заданий.
- BitNet 2B TL2 не выбирать ради скорости: выигрыш над I2_S небольшой и относится только к decode; обе реализации заметно медленнее Qwen3 0.6B.

## Как дообучать малые модели

Дообучать нужно исходную BF16/FP16-модель, не GGUF. Практичный путь — LoRA/QLoRA через Transformers + PEFT или Unsloth: собрать качественные пары `system/user/assistant` из реальных сценариев, отделить 10–15% на eval, обучать адаптер 1–3 эпохи с небольшим learning rate и остановкой по eval loss. Для backend особенно важны примеры строгого JSON, отказоустойчивые ответы и контрпримеры.

После обучения: слить LoRA с базовой моделью, конвертировать merged checkpoint в F16 GGUF через `convert_hf_to_gguf.py`, затем сделать `Q4_K_M` через `llama-quantize`. Решение принимать не по train loss, а по фиксированному набору реальных диалогов: точность полей JSON, фактические ошибки, безопасность, latency и tok/s.
