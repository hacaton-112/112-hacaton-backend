# Как работает Scenario Engine

Этот документ описывает Scenario Engine — детерминированную часть учебного
звонка в тренажёре Системы-112. Он объясняет, кто принимает решения на каждом
ходу, как открываются факты сценария, как ведётся состояние заявителя и где у
реализации сегодня остались долги.

Документ описывает состояние ветки, в которой понимание вопроса оператора
отдано модели, а правило раскрытия `after_fact` удалено.

## Короткий ответ

Звонок ведёт движок, а модель только формулирует слова. Разделение жёсткое,
потому что занятие должно быть воспроизводимым и разбираемым: если бы
содержанием распоряжалась модель, один и тот же сценарий у двух стажёров шёл бы
по-разному, и оценка перестала бы что-либо значить.

| Решение | Кто принимает |
| --- | --- |
| Какие факты заявитель вправе назвать на этом ходу | Scenario Engine |
| О чём именно спросил оператор | Модель (разбор вопроса), при отказе — слова автора |
| Какими словами заявитель отвечает | Модель (генерация реплики) |
| Каким голосом и с какой эмоцией это звучит | Scenario Engine (ступень паники и персонаж) |
| Через сколько миллисекунд заявитель начнёт отвечать | Scenario Engine (план хода) |
| Когда заявитель заговорит сам | Scenario Engine (таймер молчания) |
| Что попадёт в журнал и в разбор занятия | Scenario Engine |
| Когда звонок закончится | Оператор, преподаватель или дворник брошенных звонков |

## Состояние звонка

Состояние живёт в двух местах. Истина — журнал `call_events`: append-only
последовательность событий с актором и временем. Быстрое чтение — проекция
`call_states`: одна строка на учебную сессию, из которой движок принимает
решения, не перечитывая журнал.

Поля проекции (`CallStateSnapshot`):

| Поле | Смысл |
| --- | --- |
| `stage` | стадия звонка |
| `panicLevel` | ступень состояния заявителя, 0–4 |
| `panicChangedAt` | когда ступень менялась в последний раз — для пауз между правилами |
| `rngSeed` | зерно вариативности: один снимок звонка всегда даёт один план хода |
| `revealedFactKeys` | что заявитель уже сообщил, в порядке раскрытия |
| `callerTurns` | сколько раз заявитель говорил |
| `operatorSilenceSince` | с какого момента оператор молчит, `null` — не молчит |
| `lastInitiativeAt` | когда заявитель в последний раз заговорил сам |
| `interruptionsUsed` | счётчик перебиваний (заведён, но не используется) |
| `offeredAt`, `answeredAt`, `endedAt` | тайминги звонка |
| `lastSequence` | номер последнего события: защита от гонок при записи |

Типы событий журнала: `call.offered`, `call.accepted`, `call.declined`,
`operator.utterance`, `caller.reply`, `panic.changed`, `escalation.fired`,
`caller.initiative`, `caller.interrupted`, `fact.revealed`, `fact.rejected`,
`stage.changed`, `instructor.intervened`, `call.ended`.

Из журнала потом строятся расшифровка разговора и оценка занятия, поэтому в него
пишется сказанное как есть: ошибка распознавания и неудачная формулировка
стажёра тоже часть правды о занятии.

## Жизненный цикл

```text
          startCall              acceptCall
   ──────────────────▶ offered ──────────────▶ conversation
                          │                        │
                          │ declineCall            │ endCall
                          ▼                        ▼
                      declined                   ended
```

Стадия `wrap_up` заведена в схеме и в порядке стадий, но перехода в неё сегодня
нет ни в одном месте кода.

- `startCall` — вызов предложен. Версия сценария обязана быть опубликованной.
  Ступень паники берётся из персонажа и прижимается к границам сценария.
  Повторная доставка той же команды идемпотентна: WebSocket переподключается, и
  дубль ожидаем. Но вторая команда на сессии, где звонок уже шёл, отвергается
  как `call-already-started`.
- `acceptCall` — оператор снял трубку. Заявитель произносит `openingLine`
  автора, и эта реплика сразу попадает в журнал и в память разговора: иначе
  следующий ответ повторил бы начало звонка. Факты, которые слышны в первой
  фразе, отмечаются раскрытыми — см. «Первая реплика».
- `endCall` — звонок закрыт с причиной. Разрешено из `conversation` и
  `wrap_up`; из `ended` или `declined` любая команда даёт `call-not-active`.

## Один ход разговора

```text
  оператор нажал кнопку
           │
           ▼
   listen.start ─────────▶ отмена идущей реплики заявителя (barge-in)
           │              открытие сокета ASR и сегмента записи
           │              setOperatorSpeaking(true): таймер молчания встал
           ▼
   кадры PCM 16 кГц ────▶ Whisper + VAD          ──▶ файл записи дорожки
           │              фразы по паузам
           ▼
   listen.stop ─────────▶ сшивка фраз в одну реплику
           │
           ▼
   разбор вопроса моделью ──▶ askedFactIds
           │
           ▼
   buildGenerationContext ──▶ персона, состояние словами, разрешённые факты,
           │                  недавние реплики, уже сказанное, план хода
           ▼
   генерация реплики (до двух попыток) ──▶ текст, эмоция, revealedFactIds
           │
           ▼
   пауза из плана хода
           │
           ▼
   синтез Qwen3-TTS с голосом от движка ──▶ аудиокадры оператору
           │
           ▼
   applyCallerReply ──▶ журнал, раскрытые факты, эскалация, ступень паники
```

Ход делает сервер, а не клиент отдельной командой: тогда между распознанной
речью и ходом звонка помещался бы чужой текст.

## Понимание вопроса оператора

Порядок обратный тому, который кажется естественным: модель спрашивается
**всегда**, а ключевые слова автора — это запасной путь.

`askedFacts` вызывается до сборки контекста, и условие в нём одно: если
разборщик не передан или текст пустой — вернуть `undefined`, иначе спросить
модель. Наличие или отсутствие ключевых слов в тексте на это решение не влияет
никак.

Модель получает реплику оператора и каталог сценария, где у каждого факта есть
только идентификатор, подпись (`displayLabel`) и вопрос чек-листа —
**без содержания**, чтобы понимание вопроса не стало лазейкой к скрытым
сведениям. Ответ — только идентификаторы из этого списка; выдуманные
отбрасываются фильтром по каталогу. `temperature: 0`, срок 2,5 с, разбор
занимает около 250–400 мс.

Разобранный вопрос кешируется на пару «набор фактов + нормализованный текст», до
500 записей. Платится не за каждый ход, а за каждую новую формулировку: «какой
адрес», «адрес какой» и «Адрес?!» дают один ключ.

Когда работают ключевые слова автора:

| Случай | Что происходит |
| --- | --- |
| Разборщик не внедрён (тесты, ручные прогоны) | сравнение по `keywords` |
| Текст пустой | открывать нечего |
| Ход по инициативе заявителя | текст обнуляется: вопроса не было |
| Модель не ответила за 2,5 с, отдала не-2xx или сломанный JSON | `warn` в лог и `keywords` |

Важное следствие: когда разбор состоялся, `keywords` для доступности факта не
смотрятся вообще — это замена, а не объединение. Промах модели на понятном
вопросе стоит заявителю ответа, тогда как до появления разбора словарь автора
такой вопрос отработал бы. Обратная ошибка безопаснее: лишний идентификатор
откроет только то, что и так разрешено, — `never`, `below_panic` и остальные
правила разбор не отменяет, он подменяет проверку `on_question`.

## Правила раскрытия фактов

Правило отвечает на один вопрос: вправе ли заявитель назвать этот факт прямо
сейчас. Набор намеренно узкий и проверяется детерминированно.

| Правило | Когда факт открыт | Проверка |
| --- | --- | --- |
| `immediate` | всегда | — |
| `on_question` | оператор спросил | разбор модели, иначе `keywords` |
| `after_turns` | заявитель уже говорил N раз | `callerTurns >= turns` |
| `below_panic` | заявитель не выше указанной ступени | `panicLevel <= level` |
| `after_stage` | звонок дошёл до стадии | порядок стадий |
| `never` | никогда | — |

Каждое правило разобрано отдельно — с формой записи, примерами из сценариев и
ловушками при написании — в [`docs/disclosure-rules.md`](disclosure-rules.md).
Там же описано удалённое `after_fact` и разница между `keywords` и
`contentKeywords`.

Два ограничения, важных для чтения кода: перехода в стадию `wrap_up` нигде нет,
поэтому `after_stage` применимо только со значением `conversation`; а `level` в
`below_panic` ниже `panicFloor` версии делает факт недостижимым, и схема этого не
поймает.

## Бюджет фактов и выбор содержания

Правило делает факт доступным, но не сказанным. Дальше идут два фильтра.

**Бюджет хода** ограничивает только новые факты: 3, 3, 2, 1, 1 по ступеням
паники. Уже прозвучавшие факты остаются доступными всегда — повторяться
заявителю не запрещено, и на верхних ступенях он именно этим и занимается.
Так паника слышна как сбивчивость, без отдельных указаний модели.

**Выбор содержания** (`focusFacts`) отвечает на другой вопрос: что из
доступного относится к делу. Порядок предпочтений:

1. факты, о которых спросили по разбору модели, — если они доступны;
2. спросили ровно о том, что правило держит закрытым — заявитель не отвечает
   **ничем**: подставить вместо кода домофона номер дома хуже, чем промолчать;
3. совпадение по `keywords` правила `on_question`;
4. факт, только что ставший доступным, — но лишь на открытый вопрос вроде «что
   случилось?». На точный вопрос свежесть отвечать не вправе: иначе на «вы
   сейчас в безопасности?» заявитель рассказывал про состояние детей;
5. повтор уже сказанного — на открытый вопрос самое важное по приоритету, на
   просьбу повторить последнее сказанное.

## Как факт считается названным

Модель обязана перечислять раскрытые факты в `revealedFactIds` и регулярно этого
не делает: заявитель отвечает «Там дети!», а обязательный вопрос остаётся
открытым. Поэтому засчитывается объединение двух источников:

```text
revealed = revealedFactIds модели  ∪  факты, слышные в тексте реплики
```

Оба источника сужены разрешённым на этом ходу набором: словами открыть закрытое
нельзя. Идентификатор вне набора снимается, а сама реплика доходит до синтеза —
скрытых фактов модель не получала и раскрыть их не могла, поэтому лишняя
пометка это ошибка разметки, а не утечка. Снятие пишется в журнал как
`fact.rejected`: сигнал качества промпта, но не повод оставить оператора без
ответа.

Чем `on_question.keywords` отличаются от `contentKeywords` — таблицей в
[`docs/disclosure-rules.md`](disclosure-rules.md): первые описывают вопрос
оператора и ищутся подстрокой, вторые — ответ заявителя и сравниваются с
начала слова.

Факт без `contentKeywords` не засчитывается словами никогда: молчаливое
совпадение хуже пропуска.

## Шкала состояния заявителя

Пять ступеней, а не непрерывная величина: ступень должна быть слышна оператору и
однозначно читаться в разборе.

| Ступень | Эмоция | Интенсивность | Темп | Бюджет фактов | Заговорит сам через |
| --- | --- | --- | --- | --- | --- |
| 0 | `calm` | 0.22 | ×1.00 | 3 | никогда |
| 1 | `anxious` | 0.40 | ×1.05 | 3 | никогда |
| 2 | `anxious` | 0.60 | ×1.15 | 2 | 6 с |
| 3 | `panic` | 0.78 | ×1.22 | 1 | 4 с |
| 4 | `panic` | 0.92 | ×1.30 | 1 | 3 с |

Модель получает ступень словами, а не числом: описание состояния, правила речи
(длина фраз, право на обрывки и повторы) и два примера реплик. Примеры действуют
на стиль вернее любого описания, поэтому в промпте они помечены как образец
подачи, а не фразы для повторения.

Темп синтеза — базовый темп персонажа, умноженный на множитель ступени и
прижатый к диапазону контракта.

## Эскалация

Движение по шкале описывают правила версии сценария. Шаг всегда единичный, и за
один ход применяется одно правило: иначе голос дёргался бы на две ступени сразу,
а разбор становился нечитаемым. Ступень не выходит за `panicFloor` и
`panicCeiling`, у каждого правила своя пауза `cooldownSeconds` от последнего
изменения ступени.

| Триггер | Когда срабатывает | Реализован |
| --- | --- | --- |
| `heavy_fact_revealed` | прозвучал факт с `severity: heavy` | да |
| `forbidden_phrase` | оператор сказал запрещённое («успокойтесь») | да |
| `calming_phrase` | оператор применил приём деэскалации | да |
| `operator_silence` | оператор молчит дольше `seconds` | да |
| `norm_time_elapsed` | прошла доля норматива приёма вызова | да |
| `question_repeated` | оператор повторяет один вопрос | нет |
| `services_confirmed` | оператор подтвердил вызов служб | нет |
| `instruction_followed` | заявитель выполнил указание | нет |

Тяжёлый факт проверяется первым: произнести вслух, что внутри дети, — самый
сильный сдвиг состояния, и он не должен теряться за фразой оператора.

Сработавшее правило пишется в журнал даже когда ступень не сдвинулась — как
`escalation.fired` с `applied: false`. Иначе на потолке шкалы запрещённая фраза
оператора исчезала бы бесследно, а разбор занятия строится по журналу.

Фразы оператора влияют и на слова, а не только на ступень: запрещённая добавляет
в промпт «оператор велел ему успокоиться — такое указание заявителя только
злит», успокаивающая — «заявителю от этого чуть легче, и он это показывает».

## План хода

Тип реакции и пауза перед ответом считаются без модели, по снимку звонка и
тексту оператора. Один и тот же снимок всегда даёт один тип реакции и одну
паузу: вариативность берётся из стабильного хеша с зерном `rngSeed`.

| Реакция | Когда выбирается | Базовая пауза |
| --- | --- | --- |
| `emotional-reaction` | запрещённая фраза, инициатива или паника без ответа | 190 мс |
| `panic-refusal` | ступень 4 и реплика оператора длиннее 10 слов | 160 мс |
| `acknowledge` | успокаивающая фраза или реплика без вопроса | 260 мс |
| `repeat` | оператор попросил повторить | 280 мс |
| `answer` | есть что ответить | 330 мс |
| `clarify` | вопрос есть, ответа в сценарии нет, заявитель спокоен | 480 мс |
| `self-correct` | изредка, начиная со второго хода | 590 мс |
| `hesitate` | изредка, когда есть что ответить | 680 мс |

Пауза корректируется ступенью паники (чем выше, тем быстрее) и дрожанием до
120 мс, затем прижимается к 120–850 мс. Реакции `clarify`,
`emotional-reaction` и `panic-refusal` фактов не несут: они отвечают чувством,
а не сведениями.

Просьба повторить, открытый вопрос и вопрос вообще определяются по тексту:
открытый вопрос — по фразам вроде «что случилось» и «расскажите», вопрос вообще
— по знаку вопроса **или** по вопросительному слову, на случай когда
распознавание пунктуацию не поставило.

## Инициатива заявителя

Единственное, что происходит в звонке без действия оператора. Таймер молчания
идёт, пока `operatorSilenceSince` не `null`; он встаёт, когда оператор берёт
слово, и пока заявитель готовит или произносит реплику — иначе заявитель
заговорил бы поверх фразы, которую оператор ещё произносит.

`tick` на каждом такте проверяет правила времени, при необходимости двигает
ступень и, если молчание дольше порога ступени и прошёл
`initiativeCooldownSeconds` версии, **предлагает** транспорту реплику по
инициативе. Записывает её транспорт — тогда, когда действительно проиграет.

На инициативном ходу текста оператора нет: в журнал пишется
`caller.initiative`, а не выдуманная реплика оператора, и фактов по несуществующему
вопросу не открывается.

## Первая реплика

`openingLine` написана автором и звучит целиком, поэтому бюджет хода к ней не
применяется: бюджет ограничивает выдумку модели, а не то, что в сценарии уже
написано. Условия раскрытия при этом проверяются как обычно — факт, который
сценарий держит закрытым, первой фразой не открывается.

Факты, слышные в первой фразе, определяются по `contentKeywords` и сразу
отмечаются раскрытыми, чтобы заявитель не «сообщал» их во второй раз как
новость.

## Фоллбэк

Модель не единственная точка отказа, а звонок не вправе останавливаться.

- Ответ проверяется схемой; сила и темп речи зажимаются в диапазон, а не
  бракуются — модель регулярно понимает интенсивность как шкалу до десяти, и
  раньше из-за одного числа терялась вся реплика.
- Пересказ предыдущей реплики (не меньше трёх общих слов и не меньше 70% от
  более короткой) стоит одной попытки. На последней попытке реплика принимается:
  оставить оператора без ответа хуже, чем с повтором. При `reactionAct: repeat`
  повтор и есть требуемый ответ.
- Попыток две. После них говорит `fallbackReply`, собранный движком по плану
  хода и разрешённым фактам, и в журнал уходит `source: "fallback"`.

## Брошенные звонки

Сессия, в которой ничего не происходило 30 минут, закрывается дворником: сметает
при старте приложения и каждые 5 минут. Звонок закрывается временем последней
активности, а не временем уборки, иначе в разборе появлялись бы звонки
длительностью в десятки часов.

## Версии сценария

Звонок всегда привязан к версии, и стартовать можно только опубликованную.
Сид считает отпечаток содержимого сценария и публикует новую версию, если
отпечаток изменился, поэтому правка сценария не переписывает историю уже
проведённых занятий.

## Известные ограничения

1. **Разбор вопроса не доходит до записи хода.** `applyCallerReply`
   пересобирает разрешённый набор без разбора, потому что транспорт не передаёт
   его туда. Факт, открытый только пониманием вопроса, отклоняется:
   на «Куда ехать?» заявитель называет улицу, а в журнале появляется
   `fact.rejected`, обязательный вопрос остаётся открытым и оценка факт не
   видит. Совпал вопрос со словарём автора — всё работает.
2. **Сортировка доступных фактов не знает о разборе.** «Прямой ответ на
   вопрос» в `selectAllowedFacts` определяется по `keywords`, поэтому на
   ступенях 3–4, где бюджет равен одному факту, факт, открытый разбором, может
   проиграть фоновому факту с большим приоритетом.
3. **`never`-факты не доходят до модели**, поэтому «я не знаю» заявитель
   говорит по общей инструкции промпта, а не по тексту факта.
4. **`endCall` в ответе модели никто не читает**: повесить трубку заявитель не
   может. Поле есть в контракте и в промпте — его стоит либо начать учитывать,
   либо убрать.
5. **Три триггера эскалации не реализованы**: `question_repeated`,
   `services_confirmed`, `instruction_followed`.
6. **Перебивания не реализованы**: `maxInterruptions` версии и
   `allowsInterruption` профиля читаются, но ни на что не влияют, директива
   `caller.interrupt` не выдаётся, счётчик `interruptionsUsed` не растёт.
7. **Стадия `wrap_up` недостижима**, поэтому правило `after_stage` применимо
   только со значением `conversation`.
8. **Галлюцинации распознавания на тишине** попадают в реплику оператора
   отдельными фразами: каждая фраза распознаётся из чистого буфера, и выдумки
   Whisper больше не растворяются в одном длинном распознавании.

Понимание вопроса живёт за границей движка: порт
`ai-gateway/ports/question-understanding.port.ts`, адаптер
`ai-gateway/adapters/alice-ai/alice-ai.question.adapter.ts`, кеш и связка с
движком — `voice-pipeline/infrastructure/scenario-voice-pipeline-request.factory.ts`.
Движок не знает ни про модель, ни про сеть: ему передают колбэк, который
отвечает, о чём спросили.

## Как проверить

```bash
bun run test
```

Движок покрыт модульными тестами: правила раскрытия, отбор фактов, шкала,
переходы, план хода и жизненный цикл звонка.

```bash
bun run audit:dialogue
```

Ручной прогон по опубликованным сценариям: показывает, какой факт откроется на
заданный вопрос оператора и что заявитель ответит. Быстрее всего ловит
расхождение между тем, как сценарий написан, и тем, как он звучит.

```bash
bun run load:calls -- --clients=1 --turns=1
```

Сквозной прогон звонка через реальный ASR, модель и синтез.
