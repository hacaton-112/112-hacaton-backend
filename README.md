# Backend тренажёра Системы-112

Минимальный инфраструктурный каркас NestJS для desktop-тренажёра диспетчеров.
Старые домены шаблонного проекта удалены; сохранены только применимые к кейсу
архитектурные паттерны и интеграция PostgreSQL через Drizzle ORM.

Подробное объяснение ролей `dto`, `contracts`, `domain`, `application`, `ports`
и `infrastructure` находится в
[`docs/module-architecture.md`](docs/module-architecture.md).

## Что уже есть

- NestJS 11 и URI-версионирование API (`/api/v1`);
- централизованная конфигурация с проверкой переменных окружения;
- PostgreSQL, Drizzle ORM и команды управления миграциями;
- health check базы данных;
- JWT-авторизация и учётные записи операторов;
- единый формат API-ошибок и Zod-валидация;
- request logging с `requestId`;
- audit service для значимых действий с привязкой к учебной сессии;
- строгие Zod-контракты и потоковые порты для LLM и TTS;
- безопасная сборка потокового LLM-ответа с проверкой фактов и fallback;
- потоковый адаптер Alice AI LLM Flash через OpenAI-compatible API;
- потоковая TTS-оркестрация с проверкой PCM-протокола, retry и latency-метриками;
- заменяемые потоковые адаптеры Qwen3-TTS для MLX-Audio и vLLM-Omni;
- типизированный voice pipeline от проверенной LLM-реплики до потокового PCM;
- WebSocket transport для потоковой передачи validated reply и raw PCM клиенту;
- rate limiting и security headers.

`AliceAiAdapterModule` предоставляет `LLM_PORT` только для
`DialogueGenerationModule`, а `QwenTtsAdapterModule` предоставляет `TTS_PORT`
только для `SpeechSynthesisModule`. `AiGatewayModule` агрегирует оба адаптера для
будущих composition roots, не создавая взаимной зависимости их конфигураций.
`VoicePipelineModule` подключён к `CoreModule`; Alice AI credentials проверяются
при запуске, а для обработки голосовой команды должен быть доступен выбранный TTS
runtime. Следующими вертикальными модулями должны стать `scenarios`,
`training-sessions`, `scenario-engine`, `incident-cards` и `evaluation`.

`SpeechSynthesisModule` валидирует последовательность и метаданные PCM-чанков,
сохраняет backpressure и не буферизует аудио. Повтор допускается только до выдачи
первого чанка, чтобы клиент не воспроизводил один фрагмент дважды.

## Авторизация

`AuthModule` выдаёт JWT доступа по паролю: `POST /api/v1/auth/login` возвращает
`accessToken`, `refreshToken`, их сроки жизни и профиль, а `GET /api/v1/auth/me`
отдаёт текущего
пользователя по заголовку `Authorization: Bearer <token>`. Проверку выполняет
`AccessTokenVerifier`: он извлекает токен, сверяет подпись с закреплённым
алгоритмом и валидирует claims. Закрытые маршруты помечаются `JwtAuthGuard`.
Пароли хранятся как bcrypt-хеши, логин ограничен 5 попытками в минуту, а неверный
пароль и несуществующий email отвечают одинаково — по коду
`AUTH_LOGIN_INVALID_CREDENTIALS`.

Публичной регистрации нет: учётные записи заводит администратор.

```bash
bun run user:create -- operator@system112.ru "operator-1" "Анна Смирнова" [role]
```

Роли — `operator` (по умолчанию), `instructor`, `admin`. Обязательная переменная
окружения `JWT_SECRET` (минимум 32 символа), срок жизни токена настраивается
через `JWT_ACCESS_TTL_SECONDS`.

### Сессии и ротация

`POST /api/v1/auth/refresh` обменивает refresh-токен на новую пару, а
`POST /api/v1/auth/logout` завершает сессию и всегда отвечает `204`, чтобы по
ответу нельзя было проверить, существует ли токен. Оба маршрута открыты: access
-токен к этому моменту уже истёк.

Refresh-токен — непрозрачный секрет на 256 бит, в базе лежит только его
SHA-256. Каждый обмен выдаёт новый токен и гасит предыдущий, а повторное
предъявление уже потраченного токена отзывает **всю** цепочку сессии: украденный
токен работает лишь до первого обновления у настоящего клиента.

Отсюда требование к клиенту: обновление должно быть single-flight — один
запрос `refresh` в полёте, остальные ждут его результата. Два параллельных
обмена одним токеном неотличимы от кражи и завершат сессию.

Два независимых срока: `AUTH_REFRESH_TOKEN_TTL_SECONDS` — окно простоя одного
токена, `AUTH_SESSION_TTL_SECONDS` — абсолютный потолок цепочки, который
обновление не продлевает. Строки потраченных токенов не удаляются автоматически;
периодическая чистка старых сессий пока делается вручную.

## Scenario Engine

`ScenarioEngineModule` — единственный источник истины о происшествии и о ходе
учебного звонка. Он решает, какие факты заявитель вправе назвать на текущем
ходу, ведёт его состояние и пишет журнал; модель формулирует реплику, но фактов
не выбирает. Полное ТЗ — `scenario-engine.md` в корне рабочей папки.

Состояние заявителя — пять ступеней. Ступень задаёт эмоцию, интенсивность и темп
для синтеза, а также бюджет фактов на ход: на третьей ступени в контекст уходит
один факт вместо трёх, и речь становится сбивчивой без отдельных указаний
модели. Движение по шкале описывают правила версии — молчание оператора и
тяжёлые факты поднимают ступень, приёмы деэскалации опускают, — шаг всегда
единичный и не выходит за `panicFloor`/`panicCeiling` сценария.

Условия раскрытия фактов проверяются детерминированно: `immediate`,
`on_question`, `after_turns`, `below_panic`, `after_stage`,
`never`. Идентификатор факта вне разрешённого набора снимается, а слова реплики
доходят до синтеза: скрытых фактов модель не получает и раскрыть их не может,
поэтому лишняя пометка — ошибка разметки, а не утечка. Снятие попадает в журнал
как `fact.rejected` — сигнал качества промпта, но не повод оставить оператора
без ответа.

О чём спросил оператор, решает модель, а не список слов. Перед сборкой контекста
уходит короткий служебный запрос: реплика оператора и каталог сценария —
идентификатор, подпись и вопрос чек-листа у каждого факта, **без содержания**,
чтобы понимание вопроса не стало лазейкой к скрытым сведениям. Ответ — только
идентификаторы из этого списка, выдуманные отбрасываются. Разбор занимает около
250–400 мс, повторный вопрос берётся из кеша, а при отказе или молчании
провайдера движок возвращается к словам автора сценария и ведёт звонок как
раньше.

Условия раскрытия при этом остаются детерминированными: `never`, `below_panic`,
`below_panic` и бюджет ступени — это состояние заявителя и темп, а не словарь,
и модели они не отдаются.

Раскрытым факт считается не только по объявлению модели. У факта есть
`contentKeywords` — слова автора сценария, по которым слышно, что заявитель его
назвал; они ищутся с начала слова, поэтому «дет» находится в «детей» и не
находится в «видеть». Проверка ограничена фактами, разрешёнными на этом ходу, и
той же проверкой проходит заданная первая реплика. Так ответ «Там дети!» закрывает
обязательный вопрос даже тогда, когда модель забыла перечислить факт.

Для каждого хода движок также выбирает `reactionAct` (`answer`, `clarify`,
`acknowledge`, `hesitate`, `self-correct`, `repeat`, `emotional-reaction` или
`panic-refusal`) и короткую минимальную паузу ответа. Выбор зависит от
сохранённого seed звонка, ступени паники, доступных фактов и слов оператора,
поэтому повторный расчёт того же состояния воспроизводим. LLM получает готовый
тип реакции и только факты, относящиеся к текущему вопросу. `repeat` выбирается
только по явной просьбе оператора; при двух ошибках LLM движок выдаёт
ситуативную безопасную реплику, а источник `model`/`fallback` и метрики попыток
записываются в журнал звонка.

Оператору отдаётся область автоопределения — центр, радиус и подпись базовой
станции, — а не точка. Точный адрес остаётся фактом со своим условием
раскрытия.

### Сценарии

Демонстрационные сценарии лежат в `drizzle/seed/scenarios/*.json` и заливаются
командой:

```bash
bun run db:seed
```

Файл — исходник версии, а не формат исполнения: движок читает только базу. Та же
Zod-схема проверяет ручной ввод и черновик от ИИ-помощника, включая ссылки на
несуществующие ключи фактов.

Изменённый файл публикуется **новой версией**, а не заменяет старую: на прошлые
версии ссылаются проведённые звонки, и разбор занятия важнее удобства
загрузчика. Каталог отдаёт последнюю опубликованную версию каждого сценария,
поэтому новый звонок начинается с неё, а старый разбор открывается на той, на
которой шёл. Неизменившийся файл не делает ничего — сид сравнивает отпечаток
разобранного сценария, а не текст файла.

Конструктор использует защищённые маршруты для ролей `instructor` и `admin`:

- `POST /api/v1/scenarios/assistant/draft` принимает синтетическое текстовое
  описание и возвращает редактируемый черновик без `location`. Адрес,
  координаты и область геолокации остаются ручными полями преподавателя и не
  входят в JSON Schema модели. Описание уходит во внешний Alice AI, но маршрут
  ничего не записывает в базу;
- `POST /api/v1/scenarios` повторно валидирует весь `ScenarioSeed` и только по
  явному действию преподавателя публикует новый сценарий с неизменяемой версией
  `1`. Исходное описание сохраняется в метаданных версии для аудита;
- `GET /api/v1/scenarios/versions/:scenarioVersionId` отдаёт опубликованную
  версию целиком — в той же форме `ScenarioSeed`, которую принимает публикация,
  и с признаком `isLatest`. По нему экран сценариев строит брифинг, а
  конструктор открывает версию на правку;
- `POST /api/v1/scenarios/:scenarioId/versions` публикует правку следующей
  версией. В теле — `baseVersionId`, версия, открытая в редакторе: если за это
  время опубликована более новая, правка отклоняется с `409
SCENARIO_VERSION_STALE`, и чужая работа не затирается. Код сценария правка не
  меняет (`SCENARIO_CODE_IMMUTABLE`), чужой код персоны не принимается.

- `DELETE /api/v1/scenarios/:scenarioId` удаляет сценарий из каталога и
  отвечает `204`, в том числе на повторный запрос. Строки версий при этом не
  стираются: на них ссылаются проведённые звонки (`call_states` — с
  `restrict`), а разбор занятия обязан открываться и после удаления. Сценарий
  получает статус `archived`: он пропадает из каталога, новый звонок по нему не
  начать, конструктор его не открывает, и правка его не воскрешает. Удаление
  пишется в аудит. Демонстрационный сценарий из сида вернётся в каталог, только
  если изменится его файл: сид публикует новую версию со статусом `published`.

Прошлые версии при этом не меняются, включая заявителя: каждая версия пишет
собственную строку `caller_personas`, поэтому звонок, проведённый по старой
версии, и в разборе звучит тем голосом и той манерой, с которыми его проходили.
Каждая публикация пишется в аудит вместе с версией, на которой основана.

Точка происшествия преобразуется в редактируемую адресную подсказку отдельным
`GET /api/v1/geocoding/reverse?latitude=...&longitude=...`. Маршрут принимает
только координаты, не обращается к LLM и возвращает нормализованные `city`,
`street`, `house` и человекочитаемый `displayName`. Ошибка провайдера не мешает
сохранить точку или ввести адрес вручную.

Тем же маршрутом пользуется оператор, когда отмечает место происшествия на
карте во время звонка, но только в рамках своего идущего звонка: запрос
передаёт `trainingSessionId`. Без него оператор получает `403`, чужой или
несуществующий звонок неотличим (`404 CALL_NOT_FOUND`), а завершённый —
`403 GEOCODING_CALL_NOT_ACTIVE`. Иначе маршрут стал бы бесплатным прокси к
провайдеру карт для любой учётной записи.

По умолчанию development-конфигурация использует публичный Nominatim OSMF.
Backend передаёт идентифицирующий `User-Agent`, сериализует запросы с интервалом
не менее секунды и кеширует результат на сутки в памяти. Это соответствует
[usage policy](https://operations.osmfoundation.org/policies/nominatim/) только
для лёгкой разработки. Для production задайте `NOMINATIM_BASE_URL` собственного
экземпляра Nominatim; URL можно заменить без обновления desktop-приложения.

Помощник не меняет Scenario Engine и не публикует результат самостоятельно.
Результат модели проходит provider-схему, затем авторитетную `ScenarioSeedSchema`;
после одной исправляющей попытки некорректный черновик отклоняется.

### Классификатор происшествий

`ClassifierModule` импортирует официальный XLSX с листом `Лист1` как новую
неизменяемую версию. Отпечаток SHA-256 делает повторный импорт идемпотентным,
а новая версия остаётся черновиком до отдельного действия администратора.
Текст пути не используется как идентификатор: одинаковые формулировки в дереве
могут вести к разным конечным строкам, поэтому карточка хранит `entryId`.

- `POST /api/v1/classifiers/versions/import` — multipart-поле `file`, только
  `admin`, размер до 10 МБ;
- `GET /api/v1/classifiers/versions` — версии и предупреждения импорта для
  `instructor` и `admin`;
- `POST /api/v1/classifiers/versions/:versionId/activate` — явная активация
  администратором;
- `GET /api/v1/classifiers/active/tree` — дерево признаков активной версии;
- `POST /api/v1/classifiers/active/route` — итоговый тип, ЕКП и обязательные
  службы по `entryId` и выбранным дополнительным признакам.

Backend повторяет расчёт при сохранении карточки и не доверяет присланному
`incidentType`. В карточке хранится снимок результата и идентификатор версии:
активация нового XLSX не переписывает уже начатые и завершённые занятия.

### Учебные группы и назначения

Занятие строится из группы, назначения и попыток. Маршруты групп и назначений
доступны ролям `instructor` и `admin`; преподаватель управляет своими группами
и назначениями, которые создал сам или которые адресованы его группам,
администратор — всеми.

- `GET/POST /api/v1/groups`, `GET/PATCH/DELETE /api/v1/groups/:groupId` —
  группа с уникальным кодом и организацией. `GET /api/v1/groups/:groupId/students`
  отдаёт учеников группы со сводкой попыток: число, средний и лучший балл,
  звонки выше порога, среднее время ответа.
  Группу с назначениями не удаляют (`409 GROUP_HAS_ASSIGNMENTS`), а архивируют;
  архивировать группу с идущим занятием нельзя.
- `POST /api/v1/groups/:groupId/members`,
  `DELETE /api/v1/groups/:groupId/members/:userId` — состав группы. Каждый
  обучающийся привязан к службе (`serviceTag`).
- `GET/POST /api/v1/assignments`, `PATCH`/`DELETE /api/v1/assignments/:id` —
  назначение: версия сценария, группа или конкретный оператор, срок, норматив
  ответа, проходной порог, лимит попыток, источник карточек (`cardSource`:
  `generated`, `ticket`, `operator_call` — сформированные обучающимися, `mixed` —
  смешанный набор, ТЗ стр. 15) и
  необязательная служба. Правится и удаляется только черновик: попытки идущего
  занятия оцениваются по одним правилам.
- `POST /api/v1/assignments/:id/launch`, `.../complete`, `.../archive` —
  жизненный цикл `draft → in_progress → completed → archived`. Черновик можно
  архивировать сразу. Занятие с идущими звонками не завершается
  (`409 ASSIGNMENT_HAS_ACTIVE_ATTEMPTS`): сначала их останавливают.

Оператор видит только ленту `GET /api/v1/assignments/my` — запущенные
назначения, адресованные ему лично или его группе. Групповое назначение со
службой видят только участники этой службы. `GET /api/v1/scenarios` для
оператора ограничен теми же сценариями: без назначений каталог пуст.
Назначение с исчерпанными попытками остаётся в ленте, чтобы было видно, почему
занятие больше не запускается.

Звонок по назначению начинается командой
`{"type":"start","scenarioVersionId":"...","assignmentId":"..."}`. Попытка
резервируется **до** создания звонка, в транзакции под блокировкой назначения:
два одновременных старта не получат один номер и не превысят лимит, а второй
активный звонок оператора отсекает частичный уникальный индекс. Отказ приходит
событием `error` с кодом `assignment-attempts-exhausted`,
`assignment-attempt-active` или `assignment-unavailable`. Попытка закрывается
первым финалом — `completed`, `declined`, `cancelled_by_instructor` или
`abandoned`, — и поздний обрыв соединения не перезаписывает итог. Преподаватель
и администратор по-прежнему могут запускать сценарии без назначения.

Кабинет преподавателя:

- `GET /api/v1/instructor/live-sessions?groupId=` — идущие звонки своих групп
  со ступенью паники, чек-листом и временем в звонке;
- `POST /api/v1/instructor/sessions/:sessionId/end` с `{"reason":"..."}`
  останавливает звонок: в журнал пишется `instructor.intervened`, оператор
  получает `call.ended` с `reason: "instructor"`, действие попадает в аудит;
- `GET /api/v1/instructor/calls?groupId=` — звонки обучающихся по назначениям
  с номером попытки и баллом;
- `GET /api/v1/instructor/students/:userId` — профиль ученика своей группы,
  его статистика и звонки. Закончившиеся звонки без оценки дооцениваются при
  открытии (оценка считается при первом разборе, иначе статистика молчала бы о
  них);
- `GET /api/v1/instructor/calls/:sessionId/debrief` — разбор такого звонка.
  Запись разговора по ссылкам из разбора преподаватель тоже слушает. Чужой
  звонок неотличим от несуществующего (`404 CALL_NOT_FOUND`).

Учётные записи ведёт только администратор. `POST /api/v1/users` создаёт
учётную запись с ФИО, email, паролем и ролью, `PATCH /api/v1/users/:userId`
меняет любое из этих полей или активность. `GET /api/v1/users` поддерживает
фильтры `role`, `status=active|inactive` и поиск `search` по ФИО/email — например,
для кабинета администратора или выбора преподавателя группы. Отключение вместо
физического удаления сохраняет историю занятий; отключённый пользователь не
может войти или обновить сессию. Новый пароль, роль или состояние доступа
отзывают все refresh-сессии пользователя. Администратор не может отключить себя,
снять свою роль или убрать последнего активного администратора. Создание,
правка, смена пароля и состояния пишутся в аудит без пароля. Публичной
регистрации по-прежнему нет.

Группу правят целиком через `PATCH /api/v1/groups/:groupId`: название, код
(`409 GROUP_CODE_ALREADY_EXISTS`, если занят), организацию, статус и — только
администратор — преподавателя. Службу ученика в группе меняет
`PATCH /api/v1/groups/:groupId/members/:userId`.

### Проверка на живой базе

```bash
bun run smoke:scenario-engine
bun run smoke:training
```

Юнит-тесты работают на стабе хранилища, поэтому SQL, транзакции и

## Упражнение ДДС с готовой карточкой

`DdsExerciseModule` отделяет работу диспетчера ДДС с уже поступившей карточкой
от голосового звонка оператора Системы‑112. Карточка создаётся как неизменяемый
снимок опубликованной версии сценария и дальше проходит только по разрешённым
состояниям:

```text
Ожидает подтверждения → Принята → Начало реагирования → Прибытие
                                         → Проведение работ → Работы завершены
                      ↘ Не принята → Принята
                      ↘ Отказ от выполнения работ
```

Первый статус `Принята` или `Не принята` измеряется относительно серверного
30-секундного срока. Для `Не принята` и `Отказ от выполнения работ` обязателен
комментарий; к остальным переходам комментарий можно добавить добровольно.
Каждое действие содержит UUID события, а сохранение проверяет ожидаемый статус
и номер последовательности, поэтому повторная доставка не создаёт второе
событие, а конкурирующие команды не перескакивают через этапы.

Маршруты доступны только роли `operator`:

- `GET /api/v1/dds-exercises` — собственная очередь и история;
- `POST /api/v1/dds-exercises` — начало упражнения по опубликованной версии;
- `GET /api/v1/dds-exercises/:exerciseId` — одна собственная карточка;
- `POST /api/v1/dds-exercises/:exerciseId/transitions` — следующий статус.

Завершённое упражнение возвращает таймлайн, список нарушений и воспроизводимый
MVP-балл: 40 баллов за первичный статус в нормативе, 60 за полное завершение
реагирования или 20 за документированный отказ; порог MVP — 75. Это техническая
рубрика текущего прототипа, а не утверждённый норматив заказчика. Поле
`trainingAttemptId` оставлено как граница интеграции с отдельным модулем групп,
назначений и попыток.

## Voice pipeline

`VoicePipelineModule` объединяет `DialogueGenerationModule` и
`SpeechSynthesisModule` в поток `operator text → LLM → validation → TTS → PCM`.
Сервис сначала полностью собирает структурированный LLM-ответ, проверяет его через
Zod и разрешённые Scenario Engine факты и только затем запускает TTS. Это не
позволяет передать в синтез непроверенные JSON-дельты или выдуманные факты.

Pipeline выдаёт типизированные события с validated reply, PCM-чанками и полными
generation, synthesis и end-to-end latency-метриками. Backpressure и исходные
`Uint8Array` сохраняются. Внутренние retry выполняются только соответствующими
generation/TTS-сервисами; pipeline не повторяет LLM после ошибки синтеза.
Если генерация и сетевой обмен уже заняли минимальную сценарную паузу, новая
задержка не добавляется. Заданная сценарием первая реплика минует LLM и идёт
сразу в тот же TTS с голосом текущей ступени паники.

### WebSocket transport

Клиент подключается к `ws://<host>:<port>/api/v1/voice-pipeline/stream` и ведёт
звонок командами `start`, `accept`, `decline`, `listen.start`, `listen.stop`,
`speak`, `cancel`, `end`. Нативный клиент автоматически отправляет `accept` и
после первой реплики открывает один постоянный поток `listen.start`.

Сначала `{"type":"start","scenarioVersionId":"..."}` — сервер создаёт учебную
сессию (идентификатор выдаёт он, а не клиент) и отвечает `call.offered` с
областью автоопределения: центр, радиус и подпись базовой станции. Точного
адреса там нет, он приходит фактами по ходу разговора. Дальше `accept` даёт
`call.accepted` с заданной сценарием первой репликой и следом поток её PCM,
после чего доступен
`{"type":"speak","operatorText":"...","voiceId":"..."}`. До приёма вызова
`speak` отвергается кодом `call-state-invalid`.

С момента приёма вызова сервер сам двигает звонок раз в секунду: молчание
оператора поднимает ступень паники, и при изменении состояния приходит
`call.state` со ступенью, счётчиком чек-листа и раскрытыми фактами. Если
оператор молчит дольше, чем терпит заявитель, тот заговаривает сам — обычной
репликой по свободному каналу; в журнале это `caller.initiative`, а не
выдуманная реплика оператора.
Пока заявитель готовит или произносит ответ, таймер молчания остановлен и
перезапускается только после `audio.done`. Открытый микрофон сам по себе не
забирает слово у заявителя. Распознанная Silero VAD реплика становится
естественным barge-in и отменяет ещё идущий ответ.
Рукопожатие требует тот же заголовок `Authorization: Bearer <token>`, что и REST:
без валидного токена соединение закрывается кодом `4401`. Браузерный `WebSocket`
заголовки задавать не умеет, поэтому транспорт рассчитан на нативный клиент.
Backend последовательно отправляет JSON-события `reply.text`, `audio.start`, затем
binary WebSocket frames с raw PCM S16LE и завершает ответ событием `audio.done`.
Все JSON-события содержат `eventId`, `sessionId`, `timestamp` и `requestId`.

На одном соединении выполняется только один запрос. Новая команда `speak` отменяет
предыдущий поток; явная команда `{"type":"cancel"}` возвращает
`request.cancelled`. PCM передаётся без Base64 и промежуточного накопления, а
отправка следующего чанка ждёт завершения предыдущей WebSocket-операции.

Раз в 15 секунд сервер шлёт ping. Клиент, пропустивший ответ, отключается: сокет
брошенного клиента остаётся `OPEN` до тех пор, пока это не заметит TCP, и всё это
время звонок продолжал бы идти — тикать, поднимать панику и тратить квоту
генерации.

Факты сценария приходят из Scenario Engine, а не от клиента. Синтетический
сценарий без базы включается через `VOICE_PIPELINE_DEMO_ENABLED=true`; по
умолчанию он выключен.

### Голос оператора и запись разговора

Речь оператора идёт через backend, а не напрямую в сервис распознавания. Иначе
сервер не видит половину разговора: ни записать её, ни сделать по ней ход он не
может, а клиент мог бы прислать текст, которого никто не произносил.

`{"type":"listen.start"}` открывает постоянный поток: сервер отвечает
`listen.started` с ожидаемым форматом кадров (PCM S16LE, 16 кГц, моно), после
чего клиент шлёт двоичные кадры по 100 мс в тот же сокет. Каждый Silero VAD
финал по тишине приходит клиенту как `listen.transcript` и сразу делает ход
звонка, не закрывая ASR-сессию. `{"type":"listen.stop"}` нужен только при
отключении микрофона или завершении разговора.

Промежуточные расшифровки оператору не показываются: он работает на слух, а
текст, который переписывает сам себя, отвлекает от разговора. Пустая расшифровка
хода не делает, потерянная реплика возвращает код `listen-failed` — её нужно
повторить.

Сервис распознавания сам заканчивает фразу по паузе: он присылает финал с
`reason: "silence"`, не закрывая сокет, и слушает дальше. Каждый такой финал —
отдельная реплика оператора и отдельный ход Scenario Engine. Открытый микрофон
не считается речью сам по себе, поэтому таймер молчания продолжает работать.
Если оператор заговорит во время ответа заявителя, распознанная реплика отменит
текущий TTS и запустит новый ответ.

Запись включается переменной `CALL_RECORDING_ENABLED` и складывает обе стороны
разговора в S3-совместимое хранилище: `docker compose up -d minio` поднимает MinIO
и создаёт корзину. Каждый непрерывный участок дорожки — отдельный объект
`calls/<sessionId>/<номер>-<operator|caller>.wav`, рядом лежит `manifest.json` со
смещениями от момента приёма вызова. Отдельные объекты, а не один файл на звонок:
реплика ограничена по длине, поэтому в памяти всегда лежит немного, а сорвавшаяся
загрузка стоит одной реплики вместо всего разговора. В манифест попадает только
то, что хранилище подтвердило. Недоступное хранилище звонок не ломает.

На разборе разговор нужен целиком, поэтому `GET /api/v1/calls/:id/recording`
собирает реплики в одну дорожку: каждая на своём смещении, промежутки — тишина,
обе стороны приведены к 24 кГц. Собранная запись кладётся рядом с кусками
(`calls/<sessionId>/call.wav`) и на следующий запрос отдаётся из хранилища:
закончившийся звонок больше не меняется. Пропавший кусок стоит своих слов, а не
всей записи.

### Нагрузка

`GET /api/v1/health/runtime` показывает задержку цикла событий, память и время
жизни процесса. Чтение начинает новое окно измерения, поэтому цифры относятся к
промежутку между двумя запросами.

`bun run load:calls -- --clients=5 --turns=3` поднимает синтетических операторов,
которые принимают звонок и шлют один и тот же WAV в реальном темпе. Отчёт
разделяет распознавание, очередь перед ним и время от конца реплики до первого
байта голоса заявителя.

## Alice AI

Адаптер использует встроенный `fetch` и потоковый OpenAI-compatible endpoint
Alice AI без дополнительного SDK. В запрос передаётся только минимальный контекст:
персонаж, разрешённые Scenario Engine факты, последние реплики и текущая реплика
оператора. Provider JSON Schema фиксирует строгую структуру ответа совместимым с
Alice AI подмножеством, а все ограничения значений и разрешённые факты повторно
проверяются полным Zod-контрактом на backend. `safety_identifier` не передаётся,
поскольку Alice AI LLM Flash отклоняет этот параметр; исходный `sessionId` также
не покидает backend.

Для включения модуля потребуются `YANDEX_AI_API_KEY` и
`YANDEX_AI_FOLDER_ID`. Опциональные настройки и их значения по умолчанию приведены
в `.env.example`. Нельзя добавлять ключи или реальные записи звонков в репозиторий
и логи.

## Qwen3-TTS

`QwenTtsAdapterModule` выбирает runtime через `QWEN_TTS_PROVIDER`. Значение
`mlx-audio` использует нативный MLX-Audio на Apple Silicon, а `vllm-omni` —
vLLM-Omni, например в Linux-контейнере с CUDA. Оба адаптера реализуют один
`TTS_PORT` и передают клиенту raw PCM S16LE без Base64 и WAV-заголовков. Формат
фиксирован как mono 24 kHz. Последний непустой PCM-чанк помечается `isFinal`, а
разделённые HTTP-границей `int16` samples безопасно объединяются.

Режим задаёт `QWEN_TTS_MODE`. Совместимый `custom-voice` использует встроенного
диктора. `base-icl` выбирает синтетический WAV по сценарному `voiceId`, проверяет
его SHA-256 при старте и передаёт тот же референс с точной расшифровкой на каждый
запрос. Если точного профиля нет, допускается только явно заданный default того
же пола. MLX-Audio получает проверенный локальный путь, vLLM-Omni — сформированный
backend `data:audio/wav;base64`; произвольный путь из WebSocket не принимается.

Provider-specific запросы разделены: MLX-Audio получает `lang_code`, `instruct`
и `streaming_interval`, а vLLM-Omni — `language`, `instructions`,
`max_new_tokens` и обязательный `stream_format: "audio"`. Поскольку vLLM-Omni не
поддерживает изменение `speed` при потоковой выдаче, `speechRate` преобразуется в
контролируемую текстовую инструкцию. Параметры обоих runtime приведены в
`.env.example`.

Каждая TTS-инструкция начинается с одинакового ограничения на голос выбранного
диктора: эмоция и темп могут менять только подачу, но не тембр, высоту, возраст
или акцент. Инструкция также требует дословно произносить текст, сохранять
разборчивость и не переходить на крик, фальцет или неречевые звуки. В
`base-icl` текстовая инструкция дополняет, но не заменяет voice-clone conditioning.

### Референсные голоса

В `base-icl` у модели нет собственных дикторов: она говорит тем голосом, который
пришёл в запросе. Репозиторий везёт готовый реестр в
`assets/tts-references/reference-voices.json`, поэтому клон говорит сразу, без
подготовки. Backend читает реестр при старте, сверяет SHA-256 каждого файла и
вкладывает WAV в каждый запрос синтеза как `data:audio/wav;base64` — на
TTS-сервере настраивать нечего.

Профиль ищется по `voiceId` персоны сценария, а если его нет — берётся запасной
того же пола. Персона, для пола которой запасного нет, не заговорит вовсе:
реестр обязан покрывать оба пола, если в каталоге есть и мужские, и женские
заявители.

### Подготовка синтетического ICL-голоса

Сначала запустите текущий CustomVoice runtime и оставьте в `.env`
`QWEN_TTS_MODE=custom-voice`. Команда создаст нейтральный синтетический WAV,
точную `refText` и реестр с SHA-256:

```bash
bun run prepare:tts-reference -- --output=/tmp/system112-dylan --voice=Dylan --gender=male
```

Прослушайте `/tmp/system112-dylan/dylan.wav`. Затем переключите runtime на Base
и укажите реестр:

```dotenv
QWEN_TTS_MODE=base-icl
QWEN_TTS_MODEL=mlx-community/Qwen3-TTS-12Hz-1.7B-Base-8bit
QWEN_TTS_REFERENCE_VOICES_PATH=/tmp/system112-dylan/reference-voices.json
```

Для vLLM-Omni используйте модель `Qwen/Qwen3-TTS-12Hz-1.7B-Base`. После
перезапуска backend тот же `Dylan` в сценарии становится ключом синтетического
ICL-профиля, а не именем встроенного диктора.

### Серверный запуск с NVIDIA CUDA

Целевой серверный runtime — официальный образ
`vllm/vllm-omni:v0.28.0` с моделью `Qwen/Qwen3-TTS-12Hz-1.7B-Base`.
Сервис находится в опциональном Compose-профиле `tts-cuda`, резервирует одну
NVIDIA GPU, использует CUDA внутри контейнера и сохраняет скачанные веса в
именованном Docker volume. Обычный `docker compose up` этот профиль не запускает.

На сервере нужны Linux, NVIDIA driver, Docker Engine с Compose и NVIDIA
Container Toolkit. Сначала проверьте, что `nvidia-smi` работает на хосте, затем:

```bash
bun run tts:cuda:config
bun run tts:cuda:up
bun run tts:cuda:gpu
docker compose --profile tts-cuda ps qwen-tts
```

Первый запуск скачивает модель и может занимать несколько минут. До окончания
загрузки healthcheck показывает `starting`; прогресс доступен через
`bun run tts:cuda:logs`. Готовность API проверяется без генерации аудио:

```bash
curl --fail http://127.0.0.1:8091/health
```

Backend на том же сервере настраивается так:

```dotenv
QWEN_TTS_PROVIDER=vllm-omni
QWEN_TTS_MODE=base-icl
QWEN_TTS_BASE_URL=http://127.0.0.1:8091
QWEN_TTS_MODEL=Qwen/Qwen3-TTS-12Hz-1.7B-Base
QWEN_TTS_REFERENCE_VOICES_PATH=/absolute/path/to/reference-voices.json
```

Если синтетического референса ещё нет, его можно один раз подготовить на том же
CUDA-сервере. Сначала временно задайте в `.env`:

```dotenv
QWEN_TTS_CUDA_MODEL=Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice
QWEN_TTS_PROVIDER=vllm-omni
QWEN_TTS_MODE=custom-voice
QWEN_TTS_MODEL=Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice
QWEN_TTS_BASE_URL=http://127.0.0.1:8091
```

Пересоздайте контейнер и сгенерируйте референс:

```bash
docker compose --profile tts-cuda up -d --force-recreate qwen-tts
bun run prepare:tts-reference -- \
  --output=var/tts-reference/dylan \
  --voice=Dylan \
  --gender=male
```

Прослушайте созданный WAV. Затем верните обе настройки модели на
`Qwen/Qwen3-TTS-12Hz-1.7B-Base`, включите `base-icl`, укажите абсолютный путь к
`var/tts-reference/dylan/reference-voices.json` и ещё раз пересоздайте контейнер.
Каталог референсов исключён из Git.

После перезапуска backend выполните `bun run diagnose:tts`. Манифест диагностики
фиксирует provider, режим и SHA-256 референса, но не копирует reference audio.

API vLLM-Omni не имеет авторизации проекта и по умолчанию привязан только к
`127.0.0.1`. Если GPU runtime и backend находятся на разных хостах, задайте
`QWEN_TTS_CUDA_BIND_ADDRESS` адресом приватной сети и ограничьте порт 8091
сетевым firewall; публиковать его напрямую в интернет нельзя.

```bash
bun run db:migrate
bun run start:dev
```

## Запуск в Docker и выкладка на сервер

Backend собирается в образ по `Dockerfile` и запускается в `docker-compose.yml`
вместе с базой, MinIO, Prometheus и Grafana. Приложение и миграции входят в
профиль `app`, поэтому обычный `docker compose up -d` для разработки их не
трогает:

```bash
cp .env.production.example .env
docker compose --profile app up -d --build
```

Перед каждым запуском backend сервис `migrate` применяет миграции и выходит.
Порядок выкладки на сервер, сид сценариев, первая учётная запись, обновление,
резервные копии и HTTPS описаны в [`docs/deployment.md`](docs/deployment.md).

### Метрики и Grafana

Backend отдаёт метрики Prometheus на отдельном порту 9464, а не рядом с API:
авторизации у них нет, и в compose этот порт наружу не публикуется. Кроме
метрик процесса там есть длительность HTTP-запросов по шаблону маршрута,
открытые голосовые сессии, ожидание первого звука заявителя, сорванные ходы и
доля запасных реплик. Порт настраивается переменными `METRICS_ENABLED`,
`METRICS_HOST` и `METRICS_PORT`.

Grafana слушает `http://localhost:3001`. Источник данных и dashboard состояния
системы, backend и ASR заводятся из `observability/grafana` при старте.
Prometheus загружает recording/alerting rules из `observability/prometheus`.
Какой backend он читает, решает `PROMETHEUS_CONFIG`: `prometheus.yml` — для
контейнера из профиля `app`, `prometheus.host.yml` — для backend, запущенного
на хосте. Метрики, пороги и runbook описаны в
[`docs/observability.md`](docs/observability.md).

### Ручная проверка AI pipeline

После заполнения `.env` и запуска выбранного Qwen3-TTS runtime можно независимо
проверить каждый этап на синтетическом сценарии:

```bash
bun run smoke:voice-pipeline -- generation
bun run smoke:voice-pipeline -- tts
bun run smoke:voice-pipeline -- pipeline
```

Вторым аргументом для TTS и pipeline можно передать voice ID, например:

```bash
bun run smoke:voice-pipeline -- tts Vivian
```

Режим `generation` проверяет Alice AI, SSE, JSON и allowed-fact validation без TTS.
Режим `tts` проверяет выбранный Qwen3-TTS runtime без Alice AI. `pipeline`
запускает всю цепочку и при недоступности LLM также позволяет проверить озвучивание
безопасной fallback-реплики. Скрипт не выводит credentials; созданные `.pcm` и
`.wav` файлы сохраняются в системной временной директории, а точные пути печатаются
в результате.

### Диагностика стабильности TTS

Повторяемый набор из спокойной, тревожной и панической синтетических реплик помогает
отделить дефекты самого TTS от проблем воспроизведения в desktop-клиенте. Укажите
новую или пустую директорию: runner намеренно не перезаписывает существующие
артефакты.

```bash
bun run diagnose:tts -- --output=/tmp/system112-tts-diagnostic --repetitions=3 --voice=Dylan
```

Для голоса из встроенного каталога пол определяется автоматически. Для
пользовательского voice ID его нужно указать явно через `--gender=male` или
`--gender=female`.

В директории появятся WAV-файлы и `manifest.json`. Для каждой попытки manifest
содержит точный безопасный TTS-запрос, модель и runtime, latency, длительность,
размер и SHA-256 исходного PCM. Сравнение повторов одного case показывает дрейф
тембра, а прослушивание WAV до передачи в desktop отделяет ошибку модели от ошибки
проигрывателя.

Если рядом запущен ASR-сервис, добавьте `--asr`:

```bash
bun run diagnose:tts -- --output=/tmp/system112-tts-asr --repetitions=3 --voice=Dylan --asr
```

Runner передискретизирует синтезированный PCM с 24 до частоты ASR, распознаёт его
локальным Whisper и добавляет transcript, processing time и CER в manifest. CER
здесь диагностический: он включает ошибки сразу TTS и ASR и не должен служить
единственным критерием приёмки голоса.

Если Alice AI возвращает `400`, запустите поэтапную проверку совместимости запроса:

```bash
bun run diagnose:alice-ai
```

Диагностика останавливается на первом несовместимом этапе и выводит только
ограниченный ответ ошибки с удалёнными API key и folder ID.

## Архитектурные ограничения

- `Scenario Engine` остаётся единственным источником истины по происшествию.
- LLM формулирует ответы только из разрешённых движком фактов.
- Оценка действий оператора рассчитывается детерминированно.
- ASR, LLM и TTS подключаются через заменяемые адаптеры.
- Публичные REST/WebSocket-контракты должны быть типизированы и версионированы.
