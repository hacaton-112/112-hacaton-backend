# Система-112 · учебный тренажёр диспетчера

Программный комплекс для подготовки операторов Системы-112 и диспетчеров
дежурно-диспетчерских служб города Москвы. Обучающийся принимает учебный вызов
от виртуального заявителя, ведёт с ним живой разговор, заполняет карточку
происшествия в интерфейсе АРМ-112 и передаёт её в профильные службы.
Преподаватель ведёт занятие, наблюдает за ним в реальном времени и получает
разбор с оценкой по регламенту.

**Комплекс полностью работает в изолированном контуре на процессоре.** Ни один
запрос не покидает периметр: диалог ведёт собственная дообученная модель,
распознавание, синтез речи, карта и определение адреса — свои.

---

## Чем это интересно

**Своя модель, а не обращение к чужому API.** Заявителя играет Qwen3 0.6B,
дообученный нами на учебных диалогах (`caller.gguf`, 473 МБ). Отдельная модель
Gemma 4 E2B QAT решает служебные задачи со строгим JSON — разбор вопроса
оператора, проверку грамотности, генерацию черновиков сценариев. Обе работают
через `llama-server` на CPU.

**Работает на обычном сервере.** Ориентир — Intel Core i7-8700: шесть ядер,
никаких видеокарт. Весь голосовой тракт — распознавание, диалог, синтез —
укладывается в единицы секунд, и это измерено, а не обещано.

**Закрытый контур без оговорок.** Облачные адаптеры из проекта удалены
намеренно: пока они оставались опцией, стенд можно было настроить так, что он
уходит в интернет. Карта Москвы и области отдаётся своим TileServer из
собственных тайлов, адрес по точке определяется по ним же — офлайн.

**Заявитель ведёт себя как человек.** Scenario Engine — единственный источник
правды о звонке: он решает, какие факты заявитель уже может раскрыть, как
меняется паника, когда собеседник перебивает и когда начинает говорить сам.
Модель не может выдать того, чего сценарий не открыл: ответ проверяется на
границе и отклоняется, если в нём появилось лишнее.

## Что закрыто по бизнесу

Три пользовательских пути технического задания проходятся целиком.

### Настройка учебной среды

Преподаватель ведёт каталог сценариев: пишет вручную или заказывает черновик у
модели, правит, публикует версию. Для каждого сценария формируется **эталон
ответа ДДС**, который преподаватель подтверждает — именно с ним система
сравнивает действия обучающегося. Есть предпросмотр, контекстное поле для
коррекции сгенерированного и принудительная проверка грамотности.

### Занятие на АРМ-112

Обучающийся принимает вызов, разговаривает с заявителем голосом или текстом,
заполняет карточку: адрес на карте, тип происшествия по классификатору ЕКП,
пострадавшие, описание со слов заявителя. Классификатор сам подставляет
итоговый тип и обязательные службы — удалить обязательную службу нельзя.
Сервер оценивает полноту опроса, карточку, маршрутизацию и регламент.

### Занятие ДДС с готовой карточкой

Преподаватель выбирает категории и источник карточек — сгенерированные
системой, созданные операторами 112 или вперемешку. Диспетчер получает
случайную карточку, подтверждает приём за **30 секунд**, проходит статусы
реагирования, пишет текст ответа и завершает работу. Отказ требует
обоснования. Пока занятие идёт, следующая карточка выдаётся автоматически.

### Разбор и аналитика

| | |
| --- | --- |
| Оценка | Детерминированная: процесс, текст относительно эталона, грамотность |
| Разбор | Расшифровка разговора, покрытие пунктов эталона, противоречия, время против норматива |
| Выводы ИИ | Сильные и слабые стороны группы, рекомендации, сценарии для повторения |
| Аналитика | Успеваемость, частые ошибки, динамика, прогноз готовности к аттестации |
| Выгрузка | CSV, XLSX, PDF; сертификаты о прохождении в PDF |
| Архив | Поиск разобранных карточек по адресу, типу, периоду, службе, итогу |

## Измерено на стенде

Боевой сервер, Intel Core i7-8700, синтетические операторы шлют настоящую
русскую речь.

| Показатель | Значение |
| --- | --- |
| Одновременных звонков с полноценными ответами модели | **10** — 30 ходов из 30, ни одного отказа |
| Ответ заявителя при десяти звонках | p50 7,2 с · p95 9,0 с |
| Ответ заявителя при пяти звонках | p50 3,5 с · p95 4,4 с |
| Распознавание реплики | p50 115–150 мс, RTF 0,014 |
| Синтез речи Piper | 41–138 мс |
| Задержка цикла событий под нагрузкой | не выше 85 мс |
| Память backend | 230–270 МБ |

Заявленные в техническом задании 20 одновременных звонков на этом железе
недостижимы: ограничение — модель на процессоре, а не архитектура. Кривая
измерений и объяснение — в [ограничениях](docs/сдача/06_ограничения.md).

## Как устроено

```
            браузер (React 19, Bolid UI)
                        │  HTTPS / WSS
                  ┌─────┴─────┐
                  │  gateway  │  nginx: TLS, статика, /maps/, /asterisk/ws
                  └─────┬─────┘
                        │
                  ┌─────┴──────────────────────────────┐
                  │   backend (NestJS 11 + Fastify 5)  │
                  │   Scenario Engine · оценка · ДДС   │
                  └─┬────────┬────────┬────────┬───────┘
                    │        │        │        │
              ┌─────┴──┐ ┌───┴───┐ ┌──┴───┐ ┌──┴────────┐
              │  ASR   │ │  LLM  │ │ TTS  │ │ PostgreSQL│
              │ Sherpa │ │ своя  │ │Piper │ │  MinIO    │
              │  ONNX  │ │модель │ │      │ │ TileServer│
              └────────┘ └───────┘ └──────┘ └───────────┘
                                                Asterisk
```

Модули backend разложены по одним и тем же слоям: `domain` — чистая логика без
фреймворка, `application` — сервисы, `infrastructure` — выход наружу, `ports` —
контракты между ними. Тесты вынесены в отдельное дерево, зеркалящее исходники.

**Стек.** NestJS 11, Fastify 5, Drizzle ORM, PostgreSQL 17, контракты на Zod ·
React 19, Vite (rolldown), Bolid UI · Sherpa-ONNX Zipformer RU int8 и Silero
VAD · Piper · llama.cpp · TileServer GL с OpenMapTiles · Asterisk с WebRTC ·
MinIO · Prometheus и Grafana.

## Безопасность и эксплуатация

- Вход по JWT с ротацией refresh-токена и серверными сессиями, разграничение
  прав по ролям, TLS внутри контура.
- Журнал аудита значимых действий — включая входы, неудачные попытки, отзыв
  сессий, изменение результатов обучения — с экраном для администратора и
  автоматической чисткой по сроку хранения.
- Ежедневное резервное копирование PostgreSQL с проверкой восстановления.
- Метрики Prometheus и готовые дашборды Grafana: задержки тракта, доля
  запасных реплик, состояние очередей.

## Запуск

Нужен Docker с поддержкой compose. Две модели в репозиторий не входят из-за
размера — положите их в `models/`, как описано в [models/README.md](models/README.md).

```bash
cp .env.example .env
echo 'LLM_MODELS_DIR=./models' >> .env
sh infra/tls/generate-self-signed.sh
docker compose --profile app up -d --build
```

Открыть `https://localhost`. Учебные данные и демонстрационные учётные записи —
в [ACCOUNTS.md](ACCOUNTS.md).

Разработка одного backend без контейнеров описана в
[apps/backend/README.md](apps/backend/README.md).

## Честные границы

Мы предпочитаем называть их сами.

- Горизонтального масштабирования и отказоустойчивого кластера нет:
  вертикальное — есть, отказ отдельных узлов не проверялся.
- Двадцать одновременных звонков на текущем железе недостижимы; десять
  измерены и работают.
- Мобильная вёрстка адаптивная, но отдельного мобильного продукта нет.
- Качество распознавания и синтеза на независимой выборке не измерялось.

Полный список — в [ограничениях](docs/сдача/06_ограничения.md).
